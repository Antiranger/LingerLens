- 采集前段的播放列表持续更新，没有持续下载断流的证据；这不能排除短时缺数据。
- 用户开启的直播日志只有启动、下载和更新检查信息，没有视频掉帧或前端耗时。日志并非没开，而是原来的记录覆盖不足。
- 旧系统跟踪中，主进程的 CPU 采样权重约 83.26% 位于 Windows 窗口模块。加载匹配的微软公开符号后，主要集中于 `xxxWindowEvent`（权重 61,595,041）。这不是整机 CPU 使用率。
- 单独筛选该函数的调用栈可见 `NtUserNotifyWinEvent`、`xxxProcessNotifyWinEvent`、`PostEventMessageEx`，以及系统跟踪自身的写入函数。该栈报告包含不同事件类型，不可将其命中百分比当作 CPU 百分比。
- 这些热点来自开启系统跟踪后的时间段。跟踪保存开销可能加重后来的卡死，不能把它全部归咎于原始应用问题。也不能据此认定显卡驱动、字幕或某个外部程序有错。

原始日志、采样、符号化结果与执行记录保存在本地 `.scratch/live-stutter-20260921/`，不作为公开附件上传。

## 已修改

1. `prototype/hls-companion/web-player/player.js`：控制栏保持原有刷新频率，但文字、按钮说明和进度条范围只有变化时才写入。真实函数回归测试中，20 次相同刷新原本额外产生 160 次文字/属性写入，修复后为零。暂停按钮变化仍会及时更新。该结果只证明消除了重复写入，不代表实际掉帧降低了某个百分比。
2. `prototype/hls-companion/web-player/diagnostics-log.js` 与播放器接线：只有开启日志记录时才测量；使用已有定时器，每五秒生成一条固定规模摘要，不存储逐帧数据、字幕内容、聊天内容、Cookie 或媒体地址。
3. `prototype/hls-companion/tests/test_playback_probe.js`：覆盖实际控制栏函数重复刷新、缓冲/掉帧/耗时区分、关闭测量、异常与返回值保持、页面隐藏和媒体计数重置。

## 新日志如何解释

日志来源名为 `playback-perf`，字段为：

| 字段 | 含义 |
| --- | --- |
| ms | 实际采样窗口时长（毫秒） |
| hidden / paused / ready / rate | 页面隐藏、暂停、媒体就绪状态及播放速度 |
| ahead | 当前播放位置所在连续缓冲区还剩多少秒，不跨越缓冲缺口 |
| mediaDelta | 这段时间播放位置前进多少秒；拖动、跳转会改变它 |
| frames | 浏览器报告的总视频帧增量、掉帧增量；不可用或计数重置为 null |
| timerLateMs | 100 毫秒定时器相对计划的最大迟到量，不等同于视频帧间隔 |
| events | 等待缓冲、播放、暂停、拖动、媒体错误等事件的窗口内次数 |
| workMs | 字幕、字幕历史、弹幕、聊天历史、控制栏的调用次数、累计耗时、最长单次耗时 |

这些函数耗时只覆盖同步调用，不包含之后发生的全部绘制或显卡工作。后台页面的定时器节流不应当作前台卡顿；切换可见性时会重建基线。严重卡死期间日志无法实时写入，恢复后才可能留下定时器迟到记录；退出进程可能丢失最后一个未汇总窗口。

判断顺序：缓冲接近零且出现等待事件，先查下载/供给；缓冲充足但页面定时器明显迟到，查界面线程阻塞；某项函数耗时异常，进一步缩小到该组件；缓冲和界面响应正常却掉帧增加，则重点查视频解码/画面呈现。任何一项都需结合暂停、拖动和隐藏状态解释。
