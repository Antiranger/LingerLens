## 这份计划解决什么问题

当前有三类现象，必须分开处理：

1. 应用内部已经复现的停滞路径：字幕解码器的错误输出可能堵满管道；前端请求收到响应头后，正文读取可能无限等待。
2. 系统级现象，**重症与轻症要分开记**：切到另一块屏幕上的 Edge 后，鼠标和整机曾经冻结（重症，从未复现）；另有一次 4.65 秒的 `requestAnimationFrame` 空档（轻症，**已经录到**，见下一节）。两者签名同族，但既不能合并成一个结论，也不能当成两件无关的事。
3. 用户最初的第三个抱怨「越跑越卡」：目前仍不知道它是否已被 `disable-gpu` 那个 bug 完全解释（对照在 `desktop/main.cjs:14-33` 的注释里），还是另有第二个成分。**本文没有为它安排动作**，因为还没有能把它与第 1、2 类分开的测量。**（后续：v2 计划 §W10 已把它立为独立工作包 L1——固定配置、同一会话的长时退化测量；在 L1 之前它保持「未验收」，不能从清理第 1 类缺陷推导它已解决。顶层需求登记表见[执行记录](performance-remediation-execution-record-2026-09-17.md) §0。）**

第一类可以在不改变视频/音频分离设计的前提下做小修复。第二类需要窗口可见性、浏览器渲染进程、GPU/DWM 和系统调度的同时证据，不能用应用内修复代替根因结论。

这份计划把证据、风险和改动分开。审计阶段已经完成；当前仍遵守“先审计、不改业务代码”的决定。下面的修复步骤只有在对应的机制得到确认后才实施。

## 已录到的那一次：4.65 秒「出帧停住」（2026-09-16 12:50:58）

位置：`output/soak/lag/tree-samples.jsonl` 第 93 个样本（0 基）。采集脚本是 `.scratch/laglingo-audit/subtitle-lead/lag-measure.py`（Git 忽略），每 5 秒一次；页面内注入的脚本用 `requestAnimationFrame` 间隔和 `PerformanceObserver('longtask')` 取数。下面的数字可用 `.scratch/laglingo-audit/review-soak/analyse-soak-lag.py` 从这两个文件原样复算。

| 样本 | 本地时间 | 媒体时间 | 最大 rAF 间隔 | 累计丢帧 | 源侧 idle |
|---|---|---:|---:|---:|---|
| 92 | 12:50:53 | 727.076 s | 6.4 ms | 52 | 0 / 5.0 s |
| 93 | 12:50:58 | 732.094 s | **4650.1 ms** | 58 | 0 / 4.5 s |
| 94 | 12:51:03 | 737.156 s | 50.0 ms | 61 | 3.5 / 4.3 s |

这一次记录对三件事各自给出了**什么程度的限制**——是限制，不是排除：

- **整机没有停。** 采样器是独立 Python 进程，用 `time.time()` 打点。它在这 101 个样本上的相邻间隔是 p50 5.019 s、**最大 5.029 s**。整机真停 4.65 秒，它自己那一次间隔必然变成约 9.6 秒。**限制是**：采样节拍本身就约五秒，所以这只排除"整机恰在一次采样间隔里停了 4.65 秒"，**没有排除**采样间隙内的短停，也**没有排除显示系统单独冻结**。
- **应用的 JS 没有堵。** `longTasks` 在两个文件全部 149 个样本里都是 0，而且不是 `null`——采集脚本只在 observer 注册失败时才写 `null`。**限制是**：这只说明在 `longtask` 这个定义下没有观测到超过 50 ms 的主线程任务，**不排除**任务根本没有获得调度，也不排除页面被限频（隐藏页面本来就限频）。
- **媒体腿没有断。** 媒体时间以 5.018 秒一步正常推进，`paused=false`、`readyState=4`、前向缓冲约 7.9 秒，源侧 idle 没有越过阈值。**限制是**：`currentTime` 推进证明的是**媒体时钟在走**，不是**画面真的被呈现出来**。

**因此这一段记录的准确名字是「4.65 秒 rAF 回调空档」，不是一个已经确认的故障。** 与之相容的一个假说是"显示/合成路径停止出帧，其余一切存活"；这个假说也与「整机连鼠标都动不了」相容（光标由 DWM 合成），所以两者可能是同一现象的不同严重程度而不是两件无关的事。**但相容不是证据**：本节没有任何字段能区分"没有出帧"与"出了帧但没被合成"，也没有跨屏或遮挡字段。它是**待验证的假说**，不是已升级的 DWM 根因，也不是已确认的视频冻结。

这两个文件一共覆盖 12:38:40–12:51:33（约 13 分钟，149 个样本），其中超过 100 ms 的 rAF 间隔有 3 次：106.1 ms、237.5 ms（12:39:00，一次丢 10 帧）、4650.1 ms。超过 500 ms 的只有 1 次。

**这不能证明什么：**

- 不能证明这一次就是用户那次整机卡死。用户无法回忆发生时间（2026-09-17 询问），所以两条线必须分开记：重症未复现，轻症已录到一次。
- 不能证明触发条件与跨屏点击有关。这一次记录里没有任何 focus / visibility / 遮挡字段。
- rAF 不是视频帧。它是页面动画回调，与「显示了第几帧」不是一回事。

**因此最该补的仪器是出帧路径，不是应用内的计数器**（上面三条把应用自身 JS 与媒体腿的解释力压低了，但都没有排除它们）：

- 页面里加 `video.requestVideoFrameCallback`，拿 `metadata.mediaTime` / `presentedFrames` / `expectedDisplayTime`，区分「解码了」和「显示了」。产品代码里没有用过它，但 `.scratch/live-caption-onset-v1/browser-observer.js`（2026-09-05）已经用过——它证明这条路在本应用里走得通，不过那里只把 rVFC 当节拍器，没有取呈现时间戳。**复用那个文件时注意：它第 68 行有 `video.muted = true`，而隐藏 + 静音会挂起媒体管线，不要带过来。**
- 记录 `document.hidden` 与遮挡状态。`player.js` 现在只有 `isHidden: () => document.hidden` 一处在用，采样器一个字段都没记。
- 外部用 ETW / WPA 看 DWM 与显示调度；事后采 CPU 看不见这条路。

实验设计上有一条重要区别：**不要把目标设成「复现整机卡死」**——低概率灾难、代价高、还可能再冻一次机器。要设成「在受控触发下复现这个 4.65 秒签名」：签名可测、不用冻机器，而且是重症的轻症形态。

## 约束和变更规则

- 保留视频腿、音频腿、独立 ASR 音频腿和源时钟对齐方式。
- 每个逻辑改动单独形成可回滚提交；不把审计脚本、业务修复和配置清理混在同一提交。
- 新增机制先说明目的、生命周期、失败行为和回滚方式，再实施。尤其是 stderr 消费任务、响应取消、增量 token 状态和持久 HTTP session。
- 不接通 `RecoveryPolicy.action` 的自动重连，不自动重启下载腿，不修改 MPO、注册表或显示适配器。
- 不按进程名终止进程；只允许对事先记录的明确 PID 执行停止。用户已有的 `python -m http.server` 进程必须保留。
- 不把一次“没有再次冻结”当成根因证明；每个系统级结论都要有对照条件和重复结果。
- 当前工作区已有的停止按钮改动必须保留；业务修复只在明确文件和明确提交中进行。

## 阶段 0：建立变更和测量基线

这一步是每次实施前的固定入口，目标是避免把已有工作区改动、测试差异或外部进程误判成新问题。

1. 记录当前 Git 状态、基线提交、解释器路径、桌面进程 PID、后端子进程 PID 和现有测试结果。
2. 运行完整 Python、JavaScript 和语法检查，结果写入本次实验目录；不把实验结果写入业务日志。
3. 为应用内指标保存起始值：字幕 PCM 推进、字幕队列长度、翻译 attempts/failures/deadline/dropped、请求 pending 时长、播放媒体时间和前向缓冲。
4. 为系统级实验准备独立 kill switch 和 watchdog；先用 dry-run 检查待停止 PID，再开始任何长跑。

阶段出口：基线测试全绿，所有待停止 PID 可人工核对，且工作区差异没有被覆盖。

## 阶段 1：先做低风险的可观测性补齐

这一步只增加诊断数据，不改变播放、暂停、重连或翻译策略。它是跨屏实验和长跑验收的前提。

### 页面与播放器

采集以下事件及时间戳：

- `visibilitychange`、`focus`、`blur`、窗口显示/隐藏和页面是否被遮挡（能可靠取得时）；
- `requestAnimationFrame` 间隔、实际视频帧推进、视频 `readyState`、`paused`、前向缓冲和 dropped frames；
- JS long task、字幕/时间线/状态/诊断轮询的开始和结束；
- 请求的阶段：等待响应头、等待正文、abort、超时和最终结果。

每条记录只保留有界的最近窗口，并带有会话 ID，避免诊断本身成为长期增长源。

### 后端与系统

同时记录：字幕解码器进程是否存活、PCM 最后推进时间、stderr 诊断尾部大小、翻译队列和 provider 延迟、renderer/GPU PID 与 CPU。系统级实验需要额外打开 GPU、DWM 和 scheduler 的 ETW 采集；如果无法取得 ETW，就明确写成“应用层证据不足”，不补猜原因。

阶段出口：可以把一次事件按时间线对齐到“页面状态 → renderer/GPU → 后端媒体/字幕 → 系统事件”。如果日志字段仍无法区分两个假设，就先补字段，不进入修复。

## 阶段 2：在明确批准后验证跨屏冻结

这不是普通回归测试，可能再次冻结机器。开始前需要一次明确授权，并确认 kill switch 已经 dry-run 通过。实验过程中不修改注册表、不禁用适配器、不同时运行两条直播管线。

按以下顺序做最小对照，每个条件重复至少两次；如果机器出现持续无响应，立即停止扩大实验范围：

1. 播放窗口和 Edge 在同一块屏幕，只切换窗口焦点。
2. 播放窗口和静态 Edge 在不同屏幕，只切换窗口焦点。
3. 不打开视频的 Edge 与播放窗口在不同屏幕。
4. Edge 播放视频与播放窗口在不同屏幕。
5. 在不启动 LingerLens 的情况下重复第 4 条，作为系统对照。

每次实验要保存触发前后至少一分钟的应用、浏览器和系统事件；如果没有重现，也只得出“本条件下未重现”。只有在条件差异稳定、时间线证据一致时，才把 MPO、虚拟显示适配器或某个应用状态转换列为高可信原因。没有稳定差异时，结论保持未知，并转向 ETW/WPA，而不是修改显示设置碰运气。

## 阶段 3：第一批应用内最小修复（两个独立变更）

只有在用户确认这一批范围后实施。每项单独修改、单独测试、单独提交。

### 3A：覆盖响应正文的请求截止时间

改动范围：`prototype/hls-companion/web-player/player.js` 的 `request()` 及其 JavaScript 回归测试。

机制：让同一个 `AbortController` 和同一个可清理计时器覆盖响应头与正文读取；正常完成时清理计时器；正文超时返回现有错误路径并发出 abort。保留现有各调用点的预算和 API，不添加重试或自动重连。

验收：正常响应无残留计时器；响应头后挂住的正文在预算到期时结束；串行轮询能在下一周期继续；abort 不留下未处理 rejection；现有 JavaScript 套件全绿。

回滚：单独回退该提交即可恢复原实现。

### 3B：消费字幕解码器的 stderr

改动范围：`prototype/hls-companion/companion/subtitle_pipeline.py` 及字幕管道测试。

机制：随现有字幕任务启动一个 stderr 消费任务，按块读取并只保留有界诊断尾部；停止、异常和进程退出时按现有生命周期取消并等待该任务，确保不遗留后台读者或子进程。不得改变视频/音频分离、PCM 背压或独立 ASR 任务。

验收：合成解码器持续输出错误时 PCM 仍推进；停止时读者、解码器和管道全部退出；正常无错误输出不会产生无界缓存；字幕相关测试和完整 Python 套件全绿。

回滚：单独回退该提交即可恢复原任务集合。

## 阶段 4：先测量、再决定条件性优化

这些项目不能用“看起来会更快”作为实施理由。每项先补测量或重放数据，再决定策略。

### 4A：Soniox 未端点路径

先在真实配置的长跑和合成无端点重放中记录：未端点 token 数、每条消息处理耗时、事件循环延迟、最终文本修订次数。只有确认该路径在实际配置中可达且占用达到影响阈值，才设计增量算法。

候选设计必须说明：如何保留最终文本核对、去重、说话人、语言和切句语义；如何处理晚到 token；如何在 `<end>`/`<fin>` 后清理。禁止只截断历史数组来“止血”。

### 4B：翻译失败为什么发生（预算只是其中一小块）

**这一步要的证据大部分已经在仓库里，不需要先跑一次长跑。** 应用自己的运行日志在 `.scratch/dev-logs/`（Git 忽略）。4 份日志合计 75 条 `translation failed, showing source text only`：

| 日志 | 失败数 | TimeoutError | 兜底 `finish_reason=length` | `deadline has expired` |
|---|---:|---:|---:|---:|
| `dev-20260916-123749.log`（12:38–14:48） | 34 | 17 | 12 | 2 |
| `dev-20260916-162253.log` | 32 | 31 | 1 | 6 |
| `dev-20260916-170423.log` | 8 | 8 | 0 | 1 |
| `dev-20260917-013209.log` | 1 | 1 | 0 | 0 |
| 合计 | **75** | **57** | 13 | 9 |

这与排序有关：**主要瓶颈是 TimeoutError（57/75），也就是整条链在字幕期限里跑不完；「兜底拿不到预留」在日志里出现 9 次，是边界情况。** 所以 4B 的先后顺序不能由「哪一条复现得更干净」决定，要由这个频次决定。

`finish_reason=length`（兜底撞 `maxTokens`）12 次集中在最早那次运行；把兜底 `maxTokens` 提到 1024 之后的两轮分别是 1 次和 0 次。这条改动已经有实跑证据。

仍然缺的是**分母**（总 cue 数 / attempts），所以上表是失败计数，不是失败率。补上分母之后，再在以下策略里选定一种并写成测试：

- 剩余时间不超过 fallback 保留量时直接跳过主服务；
- 按剩余时间比例分配主服务和 fallback；
- 只有确实存在可用 fallback 时才预留时间。

策略选定前不修改 `fallback.py`，也不调用收费 API 做未经定义的对照。

### 4C：去重集合和 HTTP 连接

去重集合先按协议确认晚到/重复消息的最大生命周期，再选择时间窗、数量上限或会话边界回收；不能在收到 final 后盲目删除仍可能到达的 ID。HTTP session 复用必须先确定 provider 的创建和关闭边界，再用远程或等价 TLS 延迟对照证明收益；本地 12 次连接的观察只说明“当前不复用”。

## 阶段 5：配置清理与结构整理

这是可维护性工作，不作为性能修复的证据，也不与第一批修复合并。

1. 维护已经交付的 [88 个选项连接表](performance-audit-2026-09-17-options.md)，**不要重做**：给它补上「默认值、实际非默认来源」两列即可。注意表内行号对应审计当时的工作区快照，而源码仍被另一个会话改动，行号会漂。
2. 对 `language` 和 `hotwordsEnabled` 先决定语义：删除无效编辑字段、改成真正的消费者，还是明确标记为仅模板字段。
3. `RecoveryPolicy.action`、五个 stall 标志位和 quiet-source 日志属于结构和语义问题，先写行为测试/状态表，再另开设计变更；不借修复性能问题之名接入自动重连。

## 阶段 6：真实长跑验收

每个应用修复完成后都要做一次同配置、同直播源的长跑；不能只依赖单元测试。验收记录至少包括：

- 播放/源状态：媒体时间、前向缓冲、实际视频帧推进、dropped frames、暂停和恢复次数；
- 字幕：PCM 推进间隔、ASR 连接状态、队列长度、未端点 token 数；
- 翻译：attempts、成功、provider failure、deadline expired、dropped、queue delay P50/P95、provider delay P50/P95、ready lag P50/P95；
- 前端：请求超时阶段、轮询是否继续、visibility/focus 事件、long task 和最大实际帧间隔；
- 进程：renderer/GPU/backend CPU、内存、stderr 尾部上限和退出完整性。

验收规则：

1. 两个第一批修复各自通过针对性回归测试和完整测试套件。
2. 响应正文挂起不会让对应串行轮询永久停止；字幕错误洪流不会让 PCM 停止推进。
3. 长跑没有新增未解释的后台任务、无界日志/集合或停止后残留进程。
4. 与基线相比，翻译失败率、ready lag 和最大实际帧间隔没有因修复显著变差；如果变化，必须能由同一次配置差异解释。
5. 跨屏冻结只有在重复对照和系统证据支持时才可以结案；否则报告为“未复现、根因未知”，并保留下一轮 ETW 入口。
