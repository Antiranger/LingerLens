# FBK Multimodal Subtitle Segmenter：英语可用性核对

日期：2026-09-07。目标是判断它是否值得替换目前的英语标点规则。公开说明确认它支持英语，但这次隔离运行没有完成可比的直播回放，因此不能把论文分数当成本机结论。

## 已确认

官方说明列出 `de_en_fr_it` 与 `all_langs` 两个多模态 checkpoint；结果表包含英语（`en`）。模型输入音频和文本，输出字幕换条／换行标记。公开模型说明在：

<https://github.com/hlt-mt/FBK-fairseq/blob/master/fbk_works/SUBTITLE_SEGMENTER_AACL2022.md>

论文在 MuST-Cinema 数据上报告 `Sigma-CPL`，英语约为 87.1–88.2 / 94.4–94.6（取决于 checkpoint 与语言设置）。这不是我们的英语直播数据、不是实时端到端延迟，也不是与本地 4 秒规则同一指标。

## 本地下载与规模

从作者官方链接下载了 `de_en_fr_it` checkpoint 及配置、SentencePiece 模型、词表：

|文件|大小|
|---|---:|
|`checkpoint_avg7.pt`|497,883,034 bytes（约 498 MB）|
|`config.yaml`|538 bytes|
|`spm.model`|408,591 bytes|
|`dict.txt`|110,815 bytes|

checkpoint 用 PyTorch 安全反序列化检查，包含约 **43.15M 个模型参数**；498 MB 文件中还包含训练状态等内容，不能把整个文件大小当作推理权重大小。它仍明显大于之前的 WtP Tiny（5 MB）和 Mini（15 MB），而且还需要 80 维音频特征、Fairseq 数据处理和相应运行依赖。

文件 SHA256：`checkpoint_avg7.pt` = `6a2572c768b4901d0173107be78d557e5ba9c307b5cb220e23da38eae0c0497a`；配置、词表和 SentencePiece 的哈希见同目录下载文件。

## 为什么没有伪造“已测出延迟”

加载 Fairseq 代码时发现官方仓库针对较旧的 Python 依赖：缺少旧版 Hydra 时无法导入；补齐后又遇到 `collections.Collection` 等 Python 兼容问题，并继续触发示例目录的 `skimage` 可选依赖。模型本身没有报错，失败发生在官方训练／推理工具链初始化阶段。

我没有为了让它勉强跑起来改写 Fairseq，也没有把 498 MB checkpoint 转成未经验证的自定义 ONNX 图。若继续投入，需要建立独立的旧版 Fairseq 环境，准备符合 MuST-Cinema 格式的音频特征和上下文文本，再写一个只做单条字幕输出的适配器。那样测出的结果才有意义；在当前代码环境里硬修依赖会污染产品环境，也无法自动得到与我们的 ASR 时间戳一致的输出。

## 与当前规则的可比性

论文结论支持“专门字幕 segmenter 通常比简单字符数规则更好”，但没有证明它一定优于我们现在的 4 秒标点候选规则。我们的规则已经在 8 路英语／日语历史回放中测到：英语超过 10 秒的字幕从 19 条降到 2 条，最长跨度从 21.48 秒降到 11.34 秒；这只是字幕跨度统计，不是论文 Sigma，也没有人工语义评分。

FBK 模型即使离线质量更好，也存在三项额外风险：

1. 音频特征必须等待并处理，可能增加直播延迟；
2. 输出是模型生成的字幕标记，必须验证原始文字是否完整、每个切点能否映射回 Soniox 单元时间；
3. 498 MB 级别的权重和 Fairseq 运行时会明显增加部署复杂度，不符合“体积小、性能消耗小”的筛选条件。

## 当前结论

**FBK 是任务上更匹配的英语候选，但不是低体积、低依赖、低风险的现成替换品；本轮没有证据证明它比我们的规则更好。** 英语可以继续做一次单独的离线适配实验，但应把它视为较重的研究基线，而不是生产热路径中的小模型。

目前生产选择仍应是规则。若要继续验证 FBK，最小安全做法是把 Fairseq 固定在隔离环境，用一小段已有英语 WAV 加上对应文字做离线推理，先测：模型加载 RSS、单段 CPU P95、输出文字守恒、切点到原 ASR 单元的映射，再与 4 秒规则在同一批人工标注窗口上比较。没有这些数据之前，不建议把它接入直播。
