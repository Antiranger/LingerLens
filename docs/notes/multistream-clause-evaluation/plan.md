# 多路直播 ASR 与切句评估方案

日期：2026-09-06。状态：测试方案，尚未启动这轮直播采集或 ASR 请求。

用户明确的范围：先日语四路不同场景，再英语四路不同场景，覆盖多人讲话和快速讲话；无需翻译 API。首轮共两批、八个独立来源。既有 160 秒日语音频用于工具自检和已知问题回归，不能作为新增独立来源凑数。

## 1. 要回答的具体问题

1. 已经说完的独立请求/应答，是否仍被切句器无谓保留？已知反例：`ちょっと待って。` 在 1.516 秒确认，却在 7.422 秒提交。
2. 话头、助词/助动词链、英语名词短语和从句中间，是否被误切？
3. 连续快速讲话时，能否抓住中间可读的分句结尾，避免字幕越积越长？
4. 多人插话是否分别保留？同一人跨 ASR 条目接续是否误接到另一句话？身份标记错了时是否造成错误合并？
5. 长等待来自音频采集/发送、ASR 确认，还是本地切句决定？哪些可能靠切句改进，哪些不能？
6. 日语、英语各自的质量怎样？不得仅用跨语言总平均掩盖英语规则覆盖薄弱的问题。

## 2. 两轮、每轮四路

| 路数 | 场景 | 选台要求 | 重点复核 |
|---|---|---|---|
| A | 单人自由杂谈 | 连续有讲话，存在长句、改口、省略、插入语 | 该接的接、该切的切；短请求不应被保留数秒 |
| B | 快语速游戏直播或赛事解说 | 有持续快语速段落，非大部分时间安静玩游戏 | 快速分句、背景音、兴奋感叹；高输出频率下处理开销 |
| C | 多人聊天、联动或讨论 | 至少两位真实说话人，有插话及实际重叠 | 说话人分离、同刻内容保留、错标导致的错误接续 |
| D | 新闻、访谈主持或讲解 | 讲话较规整，音质相对清楚，包含完整叙述 | 基础对照、标点和自然停顿是否被正确使用 |

先选日语 A–D 四个独立直播，完成后再选英语 A–D。每路先 60 秒连通性/内容试采，通过后在同一连接继续采 12 分钟正式样本。不为“同时启动”强行从直播开头追赶；各路以各自第一个保留音频采样为零点。母进程同时监管四路，无须跨直播对齐语音。

两轮总计正式音频 96 分钟，连同 8 分钟试采最多约 104 分钟送入 ASR；不是计费 26 分钟。断线重试/另补来源需单独列实际音频量，不能隐藏在预算中。当前本地 Soniox 配置无每秒人民币价格，不填写虚构金额。

12 分钟是单路初始上限，不是足够多样性的保证。预先要求正式样本每路至少包含 6 分钟有效讲话；快语速路至少标出 3 段连续 10 秒以上的快语速讲话；多人路至少找到 5 处实际插话/重叠。没达到的路标为场景不足，保留数据，另选来源补该类别，不能称为覆盖完成。快速讲话按本语言独立标记/统计，不用同一个“词/秒”阈值比较日英。

优先公开可直接接收的直播，不使用登录凭据或付费内容作为默认前提。开跑时实际探测直播状态、音轨和场景，再填写准确页面链接、频道与测试时间；没有验证的直播链接不预填为“当前在播”。

## 3. 最小采集结构

不启动四个完整 Companion，不占用用户当前播放器、IPC、配置文件或现有端口。

```text
实验母进程（最多四路、固定截止时间、统一停止）
  ├─ 日语/英语 A 子进程：独立音轨获取 → 16 kHz mono PCM → 一条 Soniox 连接
  ├─ 日语/英语 B 子进程：独立音轨获取 → 16 kHz mono PCM → 一条 Soniox 连接
  ├─ 日语/英语 C 子进程：独立音轨获取 → 16 kHz mono PCM → 一条 Soniox 连接
  └─ 日语/英语 D 子进程：独立音轨获取 → 16 kHz mono PCM → 一条 Soniox 连接

每路：保存原音频 + 原始 ASR 变化与到达时间 + 当前正式切句器输出
结束后：相同输入离线回放多个候选切句器，无须再次调用 ASR
```

实现复用：

- `.scratch/clause-segmentation-v1/capture.py` 中的 Soniox 捕获方式和 `<fin>` 收尾确认。
- `companion.providers.create_asr` 与正式 Soniox adapter，使用配置的只读副本；显式 `ja` / `en`，endpoint detection 和 speaker diarization 均开启。
- `YtDlpIngest` 的单音轨模式及既有 ffmpeg 解码方法。不下载/解码视频，不启动字幕翻译、弹幕翻译、浏览器播放或完整 HTTP 服务器。
- 正式 `CaptionChunker`，保留当前版本及文件哈希，以便原样回放。

新增薄的实验入口：母进程管理四个 capture worker，每路独立目录和结束状态。所有进程隐藏启动，追踪本次创建的子进程；停止只影响这些句柄，不按进程名批量结束 Python/ffmpeg。母进程可以停止全部，也可以单停失败的一路。不得把八路同时启动代替用户要求的先日语后英语。

### 音频时间与发送节奏

直播音轨经常按片段成批到达，不能把 ffmpeg 一次输出的几秒 PCM 瞬间发给 ASR，再假装这是自然实时识别。按 PCM 采样时长以实时节奏发送，保存每块实际读到/发送开始/发送结束的单调时钟时间和采样区间。

使用有界缓冲；若音轨停顿或数据积压，标出受影响区间。不能悄悄丢音频、补静音后宣称时间连续，也不能以瞬时爆发发送追赶而继续当作正常实时样本。持续采集不健康时终止该路并保留失败状态。受影响音频可另做受控实时回放，仅这一步会新增 ASR 计费，不能算作本次直播在线延迟。

录下的 WAV 是本路实际送到 ASR 的同一段音频。单调时钟负责测耗时；采样数量负责音频位置；UTC 只作试验日期记录。没有源端权威时间时，不声称测到了主播到本机的绝对直播延迟。

## 4. 必须保存的数据

每路目录：

| 文件 | 内容与用途 |
|---|---|
| `audio.wav` | 实际发送的原声，16 kHz / 单声道 / 16-bit，供听音标注与演示 |
| `asr.jsonl` | 原始 token 文字、词时间、语言/说话人、临时或确认状态、自然 endpoint、到达时间、已发送采样前沿，以及 adapter 归一化观察 |
| `audio-timing.jsonl` | 音频块采样区间、读到/发送时间、缓冲长度和采集异常 |
| `captions.jsonl` | 当前切句器输出原文、说话人、语音起止、提交时刻、切分原因和处理耗时 |
| `status.jsonl` | 少量按秒聚合的音频/网络/CPU/内存/缓冲状态，不打印完整配置 |
| `metadata.json` | 独立来源、场景、模型、可公开选项、版本哈希、实际送入秒数、是否确认尾部、退出类型 |
| `annotations.json` | 听音标注的可切/不可切/争议位置、听感理由、说话人不确定性 |

只保存允许字段，不保存 API key、认证头、Cookie、原始鉴权配置或带凭据的播放地址。ASR 临时文字必须保留，否则无法回答“是否早就认对，只是确认得晚”。临时文字不直接拼成最终转写，必须保留其修订/替换关系。

WAV 体积：每路 13 分钟约 24.96 MB，八路约 199.68 MB（十进制；约 190.4 MiB），识别日志另计。只采音频能减少视频带宽/解码压力，但四路是否稳定和 API 是否允许四个并行会话仍需试采验证，不能根据充值成功推断配额。

## 5. 收尾与异常有效性

- 正常采样结束后停止新增音频，排空已接收的受控队列，要求 ASR 确认收尾，设置最长等待，不无期限等持久 WebSocket 自行断开。
- 记录自然产生的字幕与强制实验收尾的残句；收尾残句单独统计，不能用强制结束加速最后一条来美化在线时延。
- 一路断流不牵连另三路。重连开启新的录音/ASR session 标识；不同 session 的说话人编号不能直接当作同一个人。
- 发生 429/配额、网络关闭或长期无音频时明确报告该路失败/不完整，不增加隐蔽重试流量或用空白采样凑时长。
- 首尾 flush、采集卡顿、严重说话人错标都要进入结果说明。语义评价和正常在线延迟评价分别指出可用区间。

## 6. 核心测量口径

不是只报一个“总延迟”。对一个经听音确认可切的片段，记录：

1. **这一段何时说完**：音频中的结尾位置。
2. **识别确认等了多久**：组成该段的所有必要文字第一次全部被确认的时刻。包含直接随 final 到达的文字，不只统计 stable delta；按具体 token/说话人取值，不能借用另一人更靠后的全局前沿。
3. **我们又多等了多久**：上述文字已确认到切句器提交的时间。若规则还依赖右侧后文/端点，在报告中点明依赖何时到达，不能把这段自动归给 ASR。
4. **本地真正算了多久**：处理回调 CPU/墙钟耗时，和等待更多字区分。
5. **给翻译还剩多少余量**：以 15 秒为参考，`15 −（提交时间 − 片段语音起点）`。只能说剩多少预算，不能说一定翻译完或已经上屏。本轮不使用虚构的固定翻译耗时替代实测。

此外统计：

- 错误截断：切在词/必要成分/不可接受的分句中间。每路计数与实际切点总数都公开。
- 漏切/过度合并：已有合适断点却长时间不提交，或把独立话语接在一起。
- 不必要等待：尤其突出超过 1 秒的案例；1 秒是复核触发条件，不是声称不可超越的正确性标准。
- 重叠保留、错人合并、丢字/重字（按具体来源追踪，标点/空白规范化另列）。
- 各路 P50/P95/max、字幕跨度、每分钟错误数、慢例列表；区分自然字幕与收尾残句。

不存在人工参考时，不能仅通过“字没丢”宣称切句正确。原声里说错/改口、ASR 认错、ASR 人物编号错、切句错四类问题分开标记。

## 7. 听音标注和公平比较

先对当前基线完整回放八路；按统一规则找短句久等、超长片段、可疑切点、多人重叠，同时每路抽取均匀分布的普通片段，不能只挑最慢案例。

每路至少做 10 个 15–30 秒片段的初步详细复核（约 80 个案例），兼顾正常例和失败例；这属于探索样本，不能把其错误率冒充全体直播错误率。日语/英语都按原声校对关键内容；不确定的语义标为“有争议”，需要用户/熟悉该语言者复核，不能自称独立人工金标准。

标签先于候选策略固定：可以切、必须接、可切但不优先、有争议。断点绑定实际 token 边缘和音频位置，不按字数制造生产时间戳。

第一轮分割：每路正式样本前 8 分钟用于诊断/设计，后 4 分钟封存，仅最终验收时使用。相同主播的这类留出仍不等同于不同主播泛化；候选通过后，再补新的主播录音验证，不能称首轮已覆盖全部语言/风格。

对照策略：

- 当前正式切句器：固定版本，不临时改基线。
- 最小改进候选：保持词/助词链保护，更好地区分完整请求/应答/感叹与未完成表达。
- 必要时再做另一候选：结合真实端点/自然停顿与已有后文，或轻量本地句界判断。每个候选必须明确增加的等待和算力。

同一条直播的同一份 ASR 确认事件、按同一到达时刻回放，比较各候选。不得拿“日语 A 直播的旧版”对比“日语 B 直播的新版”，也不得把完整转写一次性喂进去，利用真实时刻尚未出现的后文取得虚假的快/准结果。

可以离线用模型辅助提出争议点，但本轮默认不调用任何额外语言模型 API。修改策略后重放历史与新样本，不再付 ASR 费用。只有比较 ASR 配置/服务时才需要重送同一音频，那是独立后续实验。

## 8. 交付和判断是否值得替换

交付：日语/英语分开四场景表；每条慢例的责任归因；至少 8–12 个带原声的代表案例演示；候选与基线的配对比较；失败/争议样本；音频完整性、实际 API 音频时长、资源开销和测试版本。

替换生产规则前至少满足：已知词内/半句误切回归不退步；新标注的独立完整话语少等待；普通样本不因追求低延迟被切碎；不同说话人不错误合并；文字保留与实际时间不变；按语言和场景报告退步，不只看总平均。若候选速度提升但切错更多，交付取舍证据而非自动称其更优。

## 9. 执行顺序与当前准备情况

1. 已阅读现有 capture、Soniox adapter、单音轨 yt-dlp 获取与原实验脚本。环境中 ffmpeg 和项目自带 yt-dlp 可用，当前 ASR 为 Soniox `stt-rt-v5`。
2. 接下来实现独立母进程/worker 及字段记录；先用现有本地录音和 fake ASR 校验四路隔离、停止、尾部、时间记录，避免把工具故障带进付费采样。
3. 开跑时寻找并探测四个实际在播日语来源，完成 60 秒试采、12 分钟正式采集；检查完数据有效性后做英语四路。
4. 完成听音样例复核和基线报告后再提出候选策略，不边采边改规则。

本文件是具体实验方案，不表示已经实现母进程、找到八个在播来源，或已经跑完八路采样。此次没有触发新的 ASR/翻译费用，没有修改产品代码或用户当前监听会话。
