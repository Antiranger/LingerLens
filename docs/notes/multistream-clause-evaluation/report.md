# 日语／英语多路直播 ASR 与切句实测

日期：2026-09-06 至 2026-09-07（北京时间）。本轮仅调用 Soniox `stt-rt-v5`；没有调用翻译 API，没有修改／部署产品代码。

## 结论

当前切句器确实仍有本地可避免的等待，不能称为最优或已经达到延迟极限。最严重的问题是未完短片段留在说话人缓冲中太久，随后跨轮次接到另一句话上；完整日语问句也可能被错误保留。另外，文本规范化不一致会丢失本来可用的逐字时间边界。

这与 ASR 自身确认耗时是不同问题：多数离散讲话确认较快，连续英语赛事解说可能确认较慢。不能把实际耗时一律描述为固定的“6 秒 + 翻译 2 秒”。

## 已复现的问题

### 1. 旧片段跨很长时间拼接（优先处理）

- 日语 APEX：`めっちゃ。`，语音 68.28–68.88 秒，在 69.906 秒确认；直到 219.500 秒才与 `これアジアサーバーでもそうやったんけど、` 一起提交。旧片段确认后又等了 **149.594 秒**，生成字幕跨度 **142.56 秒**。
- 日语新闻：`水はどこに—`，语音 111.60–112.92 秒，在 113.922 秒确认；到 185.703 秒才与 `千葉国土事務所によりますと、` 拼接，额外等待 **71.781 秒**。该案例发生时新闻音频发送稳定。
- 原因：缓存按说话人编号长期保留；自然识别结束仅关闭识别条目，没有结束无法继续的旧表达。后续同编号的新话可能沿用旧起点。
- 这不是要求把 `めっちゃ` 一律当完整句子，而是需要区分“还在说、应继续接”和“原话已经中断／这一轮已结束”。不能只提高六秒门限或增加语尾白名单。

### 2. 已完整的日语问句没有及时切出

`え、もう、もう食べないの？もう飲まないの？`，语音 132.00–135.72 秒，137.110 秒确认。当前规则直到 150.547 秒才连同后续的 `エキーちゃん行かないの？ 一緒に、一緒に行こうよ。` 提交；本地额外等了 **13.437 秒**。

词形分析把 `ない` 标成连体形，把 `の` 标成句末助词。当前规则先去掉句末助词，再只认可终止形等类别，所以完整的口语问句也被当成未结束表达。

### 3. 全角／半角比对不一致，使逐字边界退化成整段边界

最终文字先做 NFKC 规范化，例如 `？` 变成 `?`，随后却与没有做同样规范化的 token 原文比较。比较失败后退回整段文字，原来的逐字时间边界不能参与切句。该路径在日语杂谈诊断段触发 9 处；实验中统一比对后变为 0 处，仍保留原始 token 及真实时间。

另有一个低频线索：失败的足球试采中，相邻的两个 `ま`（7.74–7.80 与 7.80–7.80 秒）被 60 毫秒容差判作重复，少保留一个字。它只是在 ASR 文字保留层面的反例，尚不能断言原声正确转写应有几个 `ま`。

### 4. 英语数字结尾被误保护，完整句子也会滞留

BLAST 英语解说：`The biggest one that was the pivotal turning point was round 19.`，该句语音从 388.92 秒开始，393.235 秒时已确认完整文字。规则把 `19.` 当作需要保护的数字形式，因此没有接受句末句号，直到 478.031 秒同一编号的 `Yeah.` 到达后才一起发布。确认后额外等待 **84.796 秒**，字幕跨度 **88.32 秒**；这一路发送没有时间漂移。

直接代码复现：完整句子以 `19.` 或 `2026.` 结尾不产生切点；把 `19` 写成 `nineteen` 则正常切分。这证明长期缓冲问题跨语言存在，也证明不能把所有长等待都归因于 Soniox。数字保护规则应结合已确认的句末和后文，而非无条件禁止数字后的句号。尚未实现这一候选。

## 离线候选与验证

仅在实验脚本中试了两项小改动：统一最终文字与 token 的规范化比较；识别有限的“连体形谓语 + 句末 の + 问号”完整问句。没有调用新的 ASR 或翻译，也没有修改产品代码。旧片段跨轮次拼接的策略尚未实现。

- 同一份识别事件按原来的到达顺序回放，没有使用当时尚未出现的后文。
- 上述问句从 150.547 秒提前至 137.110 秒提交，减少 13.437 秒等待。
- 62 个既有切句回归样例通过。正常日语四个来源的诊断与留出回放均保持逐人文字保留；失败足球试采中的单字重复判断问题仍存在。
- 候选已在最后四分钟的可用留出数据上检查。完整采集的三个日语来源文字保留通过；新闻只提供了部分留出数据。相同主播留出不等于跨主播泛化。
- 整段离线回放仍是毫秒级到一百多毫秒级；没有新增网络步骤。这个小规模观察不能替代长期性能验证。
- 语义正确率和重叠召回尚未听音标注，不能仅凭回归通过就直接宣称候选最优。

## 实验有效性与资源

四路独立进程、一条音轨一路连接；Soniox endpoint detection 与 speaker diarization 开启。WAV 保存实际发送的 PCM，使用采样数量定位音频、单调时钟测到达／发送耗时。当前没有源端权威直播时间，所以未测主播到本机的绝对延迟。本轮也没有测翻译后上屏是否小于 15 秒。

日语部分存在音源跳段／停顿日志；英语部分按实际记录报告。采集有警告不一定表示语音丢失，但不能忽略：生产切句逻辑可在保存的相同音频／识别事件上复现；在线时延结论需排除受影响区间。失败／未收尾的数据不能宣称完整。

四进程 fake ASR 验证包含完整录音哈希、采样连续、实时发送、尾部确认、20 秒满缓冲取消，以及一条故障不影响其他三条。真实回放结果与采集时生产切句器输出逐条比较；完整样本同时核对逐人文字保留。

全部实际发送音频合计 **112.94 ASR 分钟**（含失败采样与替换；不是墙钟分钟）。翻译调用 **0 次**。本地没有配置每秒价格，未估算人民币费用。

## 原声复核与剩余工作

[打开本地复核页](http://127.0.0.1:8793/review.html)。页面提供每路至少 10 个正常／异常候选窗口，并为三个明确时间反例设置入口；可以播放开始片段，再跳到被拼接字幕的结尾对照。全部听音标签默认“待听音”，没有伪装成已完成的人工标注。

本轮完成的是真实采集、自动时间分析、明确代码路径复现和小候选对照。尚未完成：80 个窗口的原声语言学标注、每路快速／重叠场景的人工资格验证、断流新闻的完整留出补采，以及旧片段结束等待机制的候选实现和评价。建议先解决已确认的四条失败路径，再对照这些原声窗口验收，而不是继续调大固定时长。

文件：`capture.py` / `probe.py` 为采集和选源；`analyze.py` / `qualify.py` 为回放与筛选；`question_candidate.py` / `normalization_candidate.py` / `heldout.py` 为离线候选；`review.html` 为带音频复核材料。每路保留 `audio.wav`、`asr.jsonl`、`audio-timing.jsonl`、`captions.jsonl`、状态与 metadata。API key、认证配置、Cookie 和带鉴权播放地址未写入这些材料。
