# 直播字幕分句实验：结果与最小实现方向

日期：2026-09-06。状态：实验完成；发现并修复一处确定的尾文丢失问题；新分句策略尚未通过上线验收。

本轮以“持续讲话时可以切分，但至少应在可读的完整分句后切”为约束。没有把六秒简单改成八秒或十秒，没有替换正在运行的播放器，也没有修改持久化 ASR 配置。

## 1. 结论

1. 六秒硬切、逗号、停顿、ASR final 都不能直接证明分句完整。
2. 当前配置关闭了 Soniox 端点检测。真实录音中，稳定 token 的确认本身存在约六秒等待，不能继续假设 ASR final 只需要几百毫秒。
3. 开启自然端点检测能显著加快这段录音的稳定文字产出，但它也会结束不完整的表达。需要把“识别结果结束”和“字幕结束”分开。
4. 仅使用少量本地词法规则的分句原型仍会误切、漏切。经过原始小片段和到达批次的实验后，不能把它称为可靠的语义切句器。
5. 确定的尾文丢失 bug 已作最小修复：最终文本仅改变空格时，不再丢掉尚未发布的日语尾文。完整测试通过。

## 2. 数据与实验有效范围

使用项目已有的 `prototype/hls-companion/runtime/jinec-live-16k.wav`，16 kHz、单声道、159.9855 秒。原始 PCM SHA-256：`fa9f5b895cd43ccef3186c1fdb494e022ed3572bb908aa02010bf61719e58dbc`。

真实 ASR：当前已配置的 Soniox `stt-rt-v5`，按真实时间发送。保存 token 文字、时间戳、final 标记、响应到达时刻、已发送音频位置、归一化观察。没有保存密钥。

捕获过程的异常也保留：

| 捕获 | 结果及用途 |
|---|---|
| `soniox-evidence-stop-timeout.jsonl` | 全部音频送完，收到尾部 `<fin>` 和完整 final。实验脚本随后错误等待持久连接自行结束而超时。完整识别数据可用于回放；不能声称收到正常 `finished`。这是主回放数据。 |
| `soniox-evidence.jsonl` | 音频送完后直接关闭，在默认两秒 drain 内没有取得全部尾部 final。旧版脚本的 `completed` 只代表程序结束，**不代表尾文完整**。没有用它做完整文本验收。 |
| `endpoint-on/` | 第一次开启端点检测的尝试发生 ConnectionError，音频发送及证据不完整。排除出对照统计。 |
| `endpoint-on-retry/` | 重试的 60 秒音频全部发送，收到 `<fin>`；作为有效的端点检测对照。统计仅取语音时间前 50 秒，排除文件结束时手动 flush 的影响。 |

后续 `capture.py` 已改为等待尾部 `<fin>`，并分别记录 `tail_finalized` 和 `finished_seen`。这属于实验脚本修正，没有修改 Companion 的关闭逻辑。

另外编写了 24 个带人工允许断点的反例，以及 38 个更细粒度 token 变体。**这些时间戳和到达计划是模拟数据**。细粒度变体只在实验中按字符分配时间，不是生产时间戳算法。标签由本次分析预先编写，不是多人独立标注的语言学数据集，错误次数不能解释成所有直播的错误率。

本轮没有调用翻译模型或运行完整播放器测量。文中“加两秒／四秒翻译”均为预算模拟，不包括翻译队列、网络和显示等待。

## 3. ASR 延迟的真实分解

这里直接计算每个非空稳定 token 的：

`第一次以 final 出现的到达时刻 − token 的语音结束时间`

这与此前使用整个 observation 的 end 时间计算 `asrAdapterDelay` 是不同指标。后者可能包含尚未稳定的文字，不能据此把等待都归给切句器。

| 同一录音前 50 秒 | final token 数 | 确认延迟中位数 | P95 |
|---|---:|---:|---:|
| 端点检测关闭 | 315 | 5.929 秒 | 6.815 秒 |
| 端点检测开启 | 341 | 1.700 秒 | 4.593 秒 |

两次识别的 token 化和识别结果略有差别，因此样本数不同。这是同一音频的单次有效对照，不是多轮统计或普遍 SLA。

关闭端点检测的完整录音中，910 个非空 final token 的确认延迟中位数为 5.873 秒、P95 为 6.806 秒。已发送音频位置减 token 结束位置也得到约六秒，支持“等待主要发生在稳定证据形成阶段”，而非仅仅本地发送节奏漂移。

从原始 final 到当前 Adapter 向 Chunker 暴露文字，还存在额外等待：中位数 0，P95 2.109 秒，最大 4.344 秒。这里按忽略空白后的字符位置匹配同一段原文，原始和归一化全文均为 1060 字符，没有拿不同内容的百分位直接相减。

这些分布的 P95 **不能相加当成总 P95**。

## 4. 切分策略对照

24 个模拟案例含长分句、列举、数量范围、日语主语／接续助词、修饰名词、助动词链、错误句号和英中案例。标注了 17 个允许的内部断点。

| 策略 | 不允许的内部切分数 | 使用的允许断点数 |
|---|---:|---:|
| 当前六秒策略 | 15 | 17 / 17 |
| 只把上限改为八秒 | 14 | 13 / 17 |
| 只把上限改为十秒 | 12 | 14 / 17 |
| 只认句末标点 | 2 | 2 / 17 |
| 词法检查弱边界，句号直接通过 | 2 | 10 / 17 |
| 所有候选均检查左右文 | 0 | 10 / 17 |
| 已知所有正确标签的 oracle 参照 | 0 | 17 / 17 |

最后一行只说明“如果已经知道断点，能做到什么”，不能作为检测器准确率。

左右文原型在 24 个案例上看似通过，但把日语拆成更接近实际 Soniox 的小片段后，38 个变体中出现 8 次坏切分。将同一个响应中已到达的 token 全部入缓冲后再判断，减少到 2 次，仍未通过。例如感谢表达仍可能成为：

`もう、メンバー入ってくれて｜ありがとね。`

这里暴露的是固定表达和分句可读性判断不足。不能继续靠“看到 て 就切”来解决，也不能把测试颗粒度改粗以隐藏它。

真实回放也证伪了“只要更保守就更好”：

| 真实录音策略 | 从字幕语音起点到切句器提交的 P95 | 回放全部约 160 秒音频的 CPU 时间中位数 |
|---|---:|---:|
| 当前策略加本轮尾文修复 | 9.443 秒 | 约 11 毫秒 |
| 左右文词法原型，当前 Adapter 输入 | 16.919 秒 | 约 30 毫秒 |
| 左右文词法原型，原始稳定片段并按响应批量处理 | 16.823 秒 | 约 176 毫秒 |

CPU 是七次离线回放的中位数，排除了导入、模型加载、文件读取和网络；不是启动耗时或线上单次回调延迟。原型未引入产品依赖，实验使用机器已安装的 fugashi/UniDic。

后两项仅切句器提交就已经可能超过十五秒。漏掉可切的位置而产生过长字幕，不能算质量改进。本轮因此否决了该原型上线。

当前策略在真实回放中有 46 次 deadline 触发，但最终 cut reason 记录为标点或停顿，`hard_deadline` 文本原因数量为零。因此“hard_deadline 原因减少”也不能独立证明六秒策略不再干扰切句。

## 5. 新切句器应有的最小职责

保持一个集中管理切句的模块，不在 ASR、翻译器、播放器里各加补丁。

```text
ASR 的稳定文字和时间戳
  → 原样保留顺序；同一响应批量接收；每个 ASR item 仅负责去重和最终确认
  → 持续的待切文本缓冲，允许同一说话人的表达跨越 ASR item
  → 根据完整左文和少量右文判断可读的分句结尾
  → 在允许断点中按播放预算选择提交范围
  → 翻译该范围；保持原始语音时间；按权威媒体时钟显示
```

**识别 final 负责确认文字，不强制提交字幕。** 开启端点检测的录音中，`で、頑張り度はね。`、`ちょっと。`、`やっぱ。` 都可单独成为 ASR final。字幕模块需要能继续接后文。仅在结束监听、切换 generation 等真正结束条件下，输出剩余片段，并标明它是尾部保留，不宣称语法完整。

**边界判断负责完整性。** 左文应完成谓语、助动词和必要尾词；右文不能证明它仍是修饰关系、固定表达、数量范围或助词续接。逗号、停顿、句号、speaker change 仅提供候选证据。对跨语言／说话人不确定的输入，要保留“不确定”状态，不能通过默认猜测取得虚假的零延迟。

**预算只决定何时采用已有的合格断点。** 六秒可保留为期望长度的软参考。无需固定等到六秒，更不能在六秒或十秒时制造一个不合格断点。允许 8–10 秒的长分句，但它们是否能按起点显示，取决于这一条实际的稳定证据与翻译完成时间。

**重叠讲话需要独立保留时间范围。** 不通过截短前一句、合并不同说话人或删除重叠字幕来伪造跟上播放。说话人识别不可靠时，应记录来源不确定；不能假设相邻 ASR item 一定来自同一人。

**不要额外串行调用一个大模型来逐 token 切句。** 本轮词法原型也尚未足够可靠。后续实现必须在这里验证更可靠的分句判定，并用当前反例、原始 token 批次、更多真实多说话人音频检验。不能因为设计框架成立，就宣称具体判定器已经选型完成。

有一个不可同时满足的极端条件需要保留：一个没有合法内部断点、持续十八秒的表达，不可能在“等完整表达＋等翻译”的前提下，让译文在十五秒延迟播放的语音起点出现。oracle 案例也失败。系统应如实统计迟到，而非强拆句子来通过预算指标。

## 6. 已落地的最小修复与验证

真实主回放的 1060 个非空字符中，旧合并逻辑遗漏了尾部 59 个字符。根因是：Adapter 拼接后的稳定前缀与 final 只有空格差异，却进入按空格分词的“已发布文字被改写”分支，日语尾文因此未被追加。

最小复现：

```text
已提交：今日は晴れです。
待提交：明日は
最终文本：今日は晴れです。 明日は雨です。
旧结果：今日は晴れです。｜明日は
修复后：今日は晴れです。｜明日は雨です。
```

只在真正的文本改写处理之前增加“去掉空白后前缀完全相同”的匹配，按原 final 的字符位置取出剩余尾文。没有引入网络调用、队列、定时器或 NLP 依赖。已有真正改写的处理保持原来的测试约束。

本轮产品文件变更：

* `prototype/hls-companion/companion/caption_chunker.py`：修复空格差异导致的 final 尾文丢失。
* `prototype/hls-companion/tests/test_caption_chunker.py`：新增真实失败路径的最小回归。
* `package.json`：把原来未被主 CI 直接执行的 chunker 测试纳入主测试链。

验证：

* 修改前，新增回归明确失败，输出丢失 `雨です。`；修改后 20 个 chunker 测试通过。
* 修复后的当前策略回放完整主捕获，1060 个非空字符全部保留；旧策略少 59 个。
* `npm run ci` 通过，包括 Python / JS 语法、Provider、Pipeline、前端和 release guard。
* 实验辅助测试 4 项通过。分句候选的严格质量门槛仍失败，这是**候选被否决的证据**，不是产品 CI 失败。
