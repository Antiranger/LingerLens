# 真实直播切句案例复核

日期：2026-09-06。结论：当前切句规则不是已证明最优的方案；固定真实录音复核已发现约 5.91 秒可疑的本地额外等待。此轮只建立演示与证据，不修改产品代码、不调用付费识别或翻译服务。

## 数据实际有哪些

1. `prototype/hls-companion/runtime/jinec-live-16k.wav`：159.9855 秒，16 kHz 单声道的真实日语直播音频。
2. `.scratch/clause-segmentation-v2/live-soniox-evidence.jsonl`：同一录音前 120 秒的 567 个响应记录，包含原始文字片段、文字对应音频时间、确认状态、响应到达时间、说话人标记和归一化识别观察。这是本次演示输入。
3. `.scratch/clause-segmentation-v2/live-pipeline-results.json`：该次实验的 42 条字幕原文、译文及提交/完成时间。演示通过当前生产切句器重放原观察，逐条核对所示字幕文字、说话人、音频起止和提交时间与这份记录一致。
4. `runtime/asr_events_jinec400.json`：另有 870 个历史 ASR 事件，含 22 个完成转写事件；已发送音频范围 0.1–160 秒。可用于后续对比，但不把它当作人工标准字幕，也不在本次三例中混用其识别结果。
5. 以前的 ANNnewsCH 直播运行记录：十五分钟 run-09、六分钟 run-20 保存有识别/字幕/翻译及浏览器时间指标，浏览器分别记录 254 / 85 条字幕身份；但查到的记录不含逐句原文和译文，因此只能诊断时间链，不能据此评价语义断句。

以上不是一个多主播标注语料库；三段演示来自同一份音频，不能当成三个独立来源。Soniox 原文中存在疑似错词，中文说明仅为理解提示，最终语义评价需要听原声校对。

## 三个实例

所有时间均为录音从头开始的秒数，不是十五秒延迟后的播放位置；此处不包含翻译耗时。

| 例子 | 关注片段音频结束 | 所需文字全部确认 | 切句器提交 | 确认后继续等待 |
|---|---:|---:|---:|---:|
| `ちょっと待って。`（等一下） | 0.720 | 1.516 | 7.422 | **5.906** |
| `で、頑張り度はね。…すごい頑張ってたから。` | 46.680 | 47.516 | 47.516 | 0 |
| 从 `で、なんか見た目は。` 到 `満点だよねってなって、` | 100.920 | 107.625 | 107.625 | 0 |

第一例：ASR 的确认只用了约 0.796 秒。当前规则将 te-form 当作未必完整的结构，没有仅凭 final / 句号提交，直到下一批出现 `じゃあ` 才接受前面的切点。这个语境下「等一下」是完整请求的强候选，具有约 5.91 秒的优化空间；不能把所有 te-form 一概改成立即提交，诸如助动词续接会因此被误切。需用更多请求句/续接句的成对反例验证。

第二例：「至于努力程度嘛」是话头，后面要接内容。当前按同一说话人接续，中间另一说话人的「めちゃめちゃ頑張ってた。」在 45.5 秒独立提交，真实语音范围重叠保留。不能为了缩短数字而强制在话头后切。

第三例：最后 `って` 和 `、` 的确认时刻都是 107.625 秒，当前切句器同批提交。这一例的约 6.705 秒尾部等待发生在上游确认过程。切句器更快计算不能拿到尚未确认的字；改用临时识别文字是另一项有修改风险的产品策略，不在本轮实现。

这些例子证明“总等待”不能等同于 ASR 等待。上轮移除翻译前后句依赖有效，但不意味着切句器已无多余等待。

## 演示与校验

- `index.html`：自包含演示，内嵌三段 WAV，不需要远端服务。可双击在浏览器打开。
- `short-request.wav`、`overlap-topic.wav`、`provider-wait.wav`：从原始 WAV 按实际采样率截出的片段，无速度/内容改写。
- `measurements.json`：时间指标及输入/生产切句文件 SHA-256，支持复核版本。
- `build.py` / `template.html`：生成器与界面。

复现：`python .scratch/caption-case-review/build.py`。脚本回放当前切句器，断言演示输出与原实测记录一致，断言第一例确认后等待约 5.906 秒、第三例同批提交。已通过。

浏览器已核对第一例在 1.52 秒“文字已确认、尚未提交”、7.43 秒“已提交”，以及第三例的确认/提交时刻；播放、暂停及同步时间线正常。演示停在第一例 1.52 秒。没有为本次演示运行产品 CI，因为产品源代码未变动。

## 比继续堆规则更合适的下一步

先从至少 3–5 个独立直播来源选择 30–60 分钟样本，覆盖杂谈长句、短请求/感叹、游戏紧张场景、多人插话和音质变化。保存原音频、包括临时版本在内的完整识别变化、实际到达时间和切句输出。只下载最终字幕文件不够：它已经丢失当时的识别等待和修订过程。

听原声给切点分为“可以切 / 必须继续 / 有争议”，先固定标签，再比较候选方案；留出不同来源的一部分录音，只做最终验收，不在调规则时反复看答案。指标同时包括错误切断、漏掉可切位置、文字确认后的额外等待、十五秒超预算率和本地计算开销；保留不可切长句，而非用任意切点提高速度。

最小候选方向：保留词内部/助词链的保护，区分完整请求、应答和未完成结构；模糊位置联合使用语句结构、自然停顿/端点与少量已到达后文。候选模型可以离线辅助标注和评估，不能把额外云端模型串行放进每个切句请求里。在独立真实样本上胜过当前方案，再决定是否引入更强的本地句界分类器。
