# 多语言字幕边界小模型实测

日期：2026-09-07。任务：验证小模型是否足够轻、足够快，能否改善直播长句切分，并保留原始 ASR 时间。

## 结论

**计算速度可行，直接作为字幕分句决策器的质量尚不合格。** 下载并实测了 WtP Tiny、WtP Mini、SaT 3L SM 三个公开多语言模型。Tiny/Mini 的独立轻量 ONNX 实验进程仅约 66/99 MiB；256 字符输入 P95 约 2.38/10.59 ms。无需为每个逗号单独调用：一次输入可得到整段多个位置的边界分数。

但“普通句子结束”与“长句内部适合字幕换条的位置”并非同一任务。在截图及多语言探针中，原始模型要么漏掉希望切开的内部位置，要么把词组、名字甚至日语词内部切开。SaT 在本轮比较中更少破坏完整词组，却几乎不切长句内部。另发现 SaT 对输入末尾给出极高边界分数，即使输入只到一个尚未说完的短语；流式应用不能直接信任该分数。

本轮仅在 `.scratch/boundary-model-evaluation` 新增实验脚本、模型和结果。没有接入生产切句器，没有重启正在运行的 Companion，没有调用付费 ASR/翻译 API。现有切句问题不能因此宣布已修复。

## 环境与模型

- Windows 10，AMD Ryzen 9 9950X，16 核 / 32 逻辑处理器，系统可见内存 93.61 GiB。
- 仅 CPUExecutionProvider；ONNX 算子内部线程设为 1、算子间线程设为 1，关闭二者线程自旋。整个 Python 进程仍包含其他库创建的约 51–53 个线程。
- 实验虚拟环境使用 `--system-site-packages`，新增依赖只安装到实验目录。不是完全独立的依赖锁定环境。安装器报告过继承的 wsproto/h11 版本冲突；本轮离线 ONNX 路径未使用它们。
- wtpsplit 2.2.1、onnxruntime 1.23.2、numpy 2.2.6、transformers 5.8.1、torch 2.11.0+cu128、psutil 6.1.1、huggingface-hub 1.15.0。虽有 CUDA 版 torch，测试没有使用 GPU。
- 下载固定 revision 的公开 ONNX 权重，文件大小与 SHA256 见 `models-manifest.json`；不需要生产 API 密钥。

| 模型 | ONNX 权重文件 | 本轮模式 |
|---|---:|---|
| WtP BERT Tiny | 5.04 MB | 未做语言/文体适配的原始换行边界分数；阈值 0.01 |
| WtP BERT Mini | 14.80 MB | 同上 |
| SaT 3L SM | 427.76 MB | 原始句子边界分数；显式阈值 0.25 |

文件大小 MB 按十进制；下表进程内存 MiB 按二进制。SaT 另需约 9.10 MB tokenizer.json。“3 层”不意味着权重文件只有几 MB。

WtP 没有加载 mixtures.skops，没有做语言/文体校准或字幕任务训练。因此结果针对本轮开箱模式，不能推论经过适配的所有小模型都无效。SaT 使用 `predict_proba` 后显式应用阈值，避免本地 Path 加载时默认阈值推断不同的问题。

## 推理耗时与内存

标准 wtpsplit 接口：相同输入文本，64/128/256/512 字符，预热后每种长度测 40 次。P95 表示约 95% 的这些调用耗时不超过该数值；不是实时最坏延迟保证。

| 模型 | 64 字符 P95 | 128 字符 P95 | 256 字符 P95 | 512 字符 P95 | 加载后进程 RSS | 全部测试后 RSS |
|---|---:|---:|---:|---:|---:|---:|
| Tiny | 0.77 ms | 1.53 ms | 4.67 ms | 5.63 ms | 717.65 MiB | 803.88 MiB |
| Mini | 3.14 ms | 5.06 ms | 10.46 ms | 24.69 ms | 749.49 MiB | 836.27 MiB |
| SaT 3L SM | 5.06 ms | 7.32 ms | 12.56 ms | 22.37 ms | 1571.29 MiB | 1645.64 MiB |

标准接口导入依赖约 12 秒，单导入阶段 RSS 已约 707 MiB。随后模型加载约 0.035 / 0.057 / 2.092 秒；首次预测约 6.67 / 11.02 / 11.30 ms。依赖启动和模型启动成本不能算成每次推理成本，也不能忽略部署时的整体内存。

为区分“大依赖开销”和“小模型本身开销”，另写短文本直接 ONNX 适配实验，在独立进程中先测内存、再导入完整库作输出对照：

| 模型 | 独立进程 RSS | 依赖导入 | 模型加载 | 256 字符 P95 | 512 字符 P95 | 17 条样例与标准库最大分数差 |
|---|---:|---:|---:|---:|---:|---:|
| Tiny | 66.02 MiB | 0.218 s | 0.0148 s | 2.38 ms | 5.08 ms | 0.0 |
| Mini | 99.04 MiB | 0.260 s | 0.0370 s | 10.59 ms | 24.00 ms | 0.0 |

该适配器仅验证不超过 512 字符的窗口，不含长文拼窗、文体适配、生产调度。数字是整段实验进程内存，不能直接当成接入现有服务后的增量内存。未测 SaT 直接 ONNX 的精简内存，也未测试低配机器或 GPU。

## 真实直播记录的负载回放

读取已有日语四路 `ja-live-02`（ja-A/B/C2/D）和英语四路 `en-live-01`（en-A/B/C/D）的识别到达记录。每路约 11.5–13 分钟，录音有效时长可能短于文件到达跨度；各路并非完全相同的持续语音密度。日语 D 的原有采集不完整，因此不能据此声称全场景覆盖。

每模型调用 2149 次，其中日语 1090 次、英语 1059 次，三个模型共 6447 次。仅已确认文字改变时考虑触发：新增标点或累计新增至少 32 字符；同一 item/speaker 缓冲区一般间隔至少 250 ms，final 例外；窗口最多 384 字符并在原 ASR 单元边缘截取。

这是一种测负载的触发策略，**不是已经实现完整的字幕提交算法**。没有为被节流的末次更新补齐定时触发，因此不能用它保证待判断内容的最大等待时间。按 item/speaker 分组也是回放脚手架，不能据此认可生产使用说话人 ID 阻塞分句。

把四份相对到达时间叠在一起，使用实测单次推理时间模拟单工作线程处理，得到：

| 模型 | 日语四路服务时间 / 785 s | 英语四路服务时间 / 780 s | 英语四路服务时间占比 | 英语模拟排队 P95 / 最大 |
|---|---:|---:|---:|---:|
| Tiny | 0.338 s | 1.778 s | 0.228% | 0 / 3.94 ms |
| Mini | 1.187 s | 6.702 s | 0.859% | 0 / 17.17 ms |
| SaT | 4.410 s | 10.036 s | 1.286% | 0 / 19.80 ms |

上表是**用记录叠加的队列模拟**，不是重新开四路直播的并发实测；服务时间占比也不是任务管理器测得的 CPU 百分比。不包含采音、ASR、翻译、播放器的开销，不代表全应用能达到同样总延迟。对于本轮稀疏触发负载，纯模型计算没有形成明显积压。

## 为什么质量仍不够

测试包含 4 条截图转录与 13 条人工构造控制文本，共 17 条，覆盖英、日、西、韩。西/韩没有真实直播回放或母语人工复核。下面列的是可复核反例，不是全面质量排名。

1. 截图 `...here in our office, to which people have offered...`：希望可以在 `office,` 后换条。三者完整上下文分数分别 0.00591 / 0.00119 / 0.00016，在上述阈值下全部不切。
2. 截图 `...the last 3 times, which have generated $55.6 million...`：希望在 `times,` 后切。Mini/SaT 保留整句；Tiny 反而切成 `...the last | 3 times, which have generated | $55.6 million...`。
3. 截图 `...why this is so crucial: the last time I opened this opportunity...`：Tiny/Mini 在冒号后切了，但又切出孤立的 `the last time`，仍不适合阅读。SaT 在 0.25 下整句不切；降低到 0.1 可选冒号，不能因此推论其他内部位置也会变好。
4. 英语名字控制 `New York University`：Tiny 在 0.01 下把名字切碎。日语 `聞こえなかったら`：Tiny 直接给出 `聞 | こえなかったら`。
5. 清楚用句号分隔的英、日、西、韩完整句子，三者在本轮默认阈值下均能找到标注的句间边界。这表明能力与我们希望的“长句内可读分句”存在任务差异。

只看 11 个预先指定的可读内部切点与 24 个禁止点，阈值变化结果如下。另有 8 个完整句间正例，未计入此表的“内部切点”。这些是少量人工探针，不是准确率；禁止点也没有穷尽所有坏切点。

| 模型 | 阈值 | 找到内部可读点 / 11 | 误选指定禁止点 / 24 |
|---|---:|---:|---:|
| Tiny | 0.01 | 3 | 5 |
| Tiny | 0.001 | 11 | 16 |
| Mini | 0.01 | 2 | 3 |
| Mini | 0.001 | 9 | 7 |
| SaT | 0.25 | 0 | 0 |
| SaT | 0.1 | 1 | 0 |
| SaT | 0.001 | 3 | 0 |

仅降低阈值不是已验证的修复。仅限制模型在逗号处选择，可以挡住部分词内部误切，但挡不住列举逗号误切，而且会漏掉没有逗号的分句。该候选限制的组合策略本轮没有进行完整质量评测。

完整逐条输出见 `examples.md`，逐点分数和上下文变化见三个 `*-1t-results.json`。

## 流式输入末尾偏置

SaT 对截图中明确未完成的 `...tens of`：

| 模型能看到的内容 | `of` 后边界分数 |
|---|---:|
| 输入恰好结束于 `tens of` | 0.999975 |
| 多看到后面 8 个字符 | 0.000193 |
| 完整截图句子 | 0.0000129 |

模型可见文本到此为止，不代表人已说完。这里只能确认观察到的输入末尾偏置，尚未验证其具体训练成因。不能将接近 1 的数值解释为经过字幕场景校准的“99.9% 可以切”。

若为每个候选点固定等待更多后文，可以降低这种误判，却可能引入新的识别/说话等待。这与模型几毫秒的计算时间是两回事。未来方案必须单独测“等候足够上下文的时间”和“执行模型的时间”，不能用后者替代前者宣称低延迟。

## 时间戳与原文保留验证

模型负责输出字符位置分数；只有能映射到原始 ASR 单元边缘的位置才有资格成为时间切点。在模型 tokenizer 内重新分词，不会获得新的声学时间；不能按字数平均分配时间。

`summarize.py` 从原始八路记录重新重建每次推理的输入窗口，对保存的候选边界逐个校验：

- 三模型共 6447 次窗口重建与原调用的到达时间、字符数一致。
- Tiny 3320、Mini 3323、SaT 2756 个候选边界的左侧结束时间、右侧开始时间均精确对应原始 ASR 单元，共 9399 个边界检查通过。
- 每次窗口按边界分片，所有片段重拼后等于规范化输入文字；原 ASR 单元不遗漏、不重复。每片开始/结束取该片单元的最早开始/最晚结束，不人为移动下一片时间。
- 这些“边界”使用回放脚本统一阈值 0.01，仅验证映射和分片；SaT 的这组候选不能称为它默认阈值 0.25 的实际字幕输出。重复窗口内同一位置会被再次检查，9399 不是独立句子数量。

例如 Mini 的 en-A 回放在 10.454 s 收到的窗口按诊断候选分为 `I gave`（0.18–0.42 s）、` Bruno ... Bruno.`（0.60–3.36 s）和后续片段。时间映射正确，但 `I gave` 单独成条显然不好：**时间正确与切句正确必须分别验收。** 本实验没有验证生产字幕发布、替换、翻译或调度链路。

## 建议与下一步边界

1. 目前不把这三个原始模型直接接入生产作为切句裁决者。优先保留本轮结果作基线，不能因为计算快就默认文字质量合格。
2. 若继续模型路线，先建立真实直播中的“可切 / 不可切 / 尚缺后文”标注，按直播来源隔离训练和验证；同时保存每个候选点首次具备足够信息的到达时间。真正优化的是直播内部可读边界，而非句号识别。
3. 在相同数据上比较现有规则、受限候选模型评分、必要时经任务适配的小模型；评价误切、漏切、长条分布、首次可提交时间和每次推理开销。模型必须实测胜出才值得接入。训练或适配能改善多少尚无证据。
4. 若后来接入，采用一段短窗口一次评分、只对变化内容触发、在有界工作线程执行并复用模型；不能每个逗号调用一次，也不能在播放器/网络事件循环里同步执行推理。需要保证最后一次待处理更新最终被判断，并避免建立多说话人独立长等待队列。这些是后续设计约束，本轮没有实施。

## 文件与复现

- `download_models.py` / `models-manifest.json`：固定版本下载与校验记录。
- `cases.json`：截图及多语言控制文本、指定正负边界。
- `evaluate.py`：标准模型 CPU 测速、上下文长度探针、八路记录负载回放。
- `lean_probe.py`：Tiny/Mini 短输入直接 ONNX 测速、内存和标准库对照。
- `summarize.py`：阈值计数、四路模拟、原始时间边缘与分片完整性检查。
- `*-1t-results.json`、`*-1t-*-jobs.json`、`*-lean.json`：原始测量。
- `analysis-summary.json` / `examples.md`：汇总数据与逐条可读输出。

在仓库根目录 PowerShell 中设置 `$env:PYTHONUTF8='1'`，用 `.scratch/boundary-model-evaluation/venv/Scripts/python.exe` 执行对应脚本。`evaluate.py` 接模型名 `wtp-bert-tiny`、`wtp-bert-mini` 或 `sat-3l-sm`；`lean_probe.py` 仅支持前两者；`summarize.py` 不调用模型，只读取现有结果与录制记录。

此次完成三个模型的离线推理/负载测量、两个模型的轻量接口等价检查、全量记录候选映射检查。未运行生产测试套件，因为没有更改生产代码；未重新连接直播进行端到端验证。
