# 说话人语调鲁棒性：五张 ticket 为什么没有效果 —— 复盘与重做方案

> 本文所有数字都是在 `F:/Projects/LagLingo` 本机实测的，数据源是
> `.benchmark-data/crema-mini/AudioWAV`（240 条 / 20 actor / 16k mono / 中位 2.34s）
> 和 `vendor/models/diarization/campplus.onnx`。实验脚本见文末附录。
>
> **先更正我自己**：上一版 `speaker-intonation-robustness-plan.md` 里的 L1.1（多子窗聚合）
> 和 L1.3（静音裁剪）是**错的**，实测为负收益，详见 R3。当时的推理
> 「语调波动是时间局部的，跨窗平均可以平掉」不成立 —— 在 2–3 秒这个时长区间，
> 切短窗损失的说话人信息远大于它平掉的语调噪声。现在实现里的 pooling 代码应当删掉。

---

## 0. 一句话结论

五张 ticket 的工程量绝大部分花在了**一个不可能通过的 gate** 上，而真正能解决问题的那个机制
（跨句证据累积）**被自己代码里的一个常量锁死了**。当前 benchmark 的理论天花板是 B³ F1 ≈ 0.69，
已交付的 0.598 已经是天花板的 87%；同时这个 benchmark 复现的是**「全部并成一个人」**，
和用户报告的**「一个人被拆成多个人」**方向相反。

---

## 1. 诊断：六个根因，按严重度排序

### R1 — 整个阈值家族写在一个不存在的分数尺度上（致命）

实测 CAM++ 在这批数据上的**真实同人 cosine 分布**：`mean=0.582, p50=0.589, p95=0.758, max=0.931`。

对照 `AssignmentConfig` 的默认值，看每个阈值**有多少比例的真·同人样本能够到**：

| 常量 | 值 | 真同人可达比例 | 后果 |
|---|---:|---:|---|
| `match_threshold` | 0.82 | **0.76%** | 几乎不可能匹配上已有 speaker |
| `candidate_match_threshold` | 0.78 | **3.03%** | 同一新人的两句进不了同一个 candidate |
| `candidate_internal_threshold` | 0.80 | **1.52%** | `_candidate_ready` 几乎恒为 False → **新说话人永远确认不了** |
| `ambiguous_low` / `new_speaker_ceiling` | 0.68 | 21.29% | 迟滞中间带形同虚设 |
| `profile_update_threshold` | 0.88 | **0.08%** | **profile 永远不累积证据**（见 R2） |
| `prototype_update_threshold` | 0.90 | **0.08%** | 多原型机制从不生效 |
| `merge_threshold` | 0.90 | **0.08%** | reconciliation 从不合并 |
| `merge_immediate_threshold` | 0.97 | **0.00%** | 死代码 |

74% 的 UNKNOWN 直接来自 `candidate_internal_threshold=0.80`（`speaker_attribution.py:525`）。

handoff 把这称为「参数过于保守」—— **不是保守，是量纲错了**。这些数字看起来像是照着
「说话人验证的余弦一般在 0.8 以上」这类经验直觉写的，但那是**长时干净语音 + 归一化 embedding**
的经验值，和本项目 2 秒短句上的实际分布差了一整个量级。

而 benchmark 的标定只覆盖了 `match_threshold` 一个
（`crema_mini.py:600`、`crema_mini.py:653`），其余全部留在不可达默认值上。所以
handoff 第 3 步说的「要标定完整状态机参数」是对的，但它没意识到**这不是调优问题，是 bug**。

### R2 — 唯一真正有效的机制被一个常量锁死（最深的一处）

实测「把同一说话人的 N 条 utterance embedding 平均后再比对」的 EER（centering 后）：

| 平均条数 | 累计语音 | EER |
|---:|---:|---:|
| 1 | ~2.4s | 16.61% |
| 2 | ~4.8s | **6.61%** |
| 3 | ~7.2s | **3.04%** |
| 4 | ~9.6s | **1.25%** |

**累积 4 条就是 13 倍的误差下降。** 这是整个系统里杠杆最大的机制，没有之一。

而 `assign()`（`speaker_attribution.py:432-438`）要求
`best_score >= 0.88 and margin >= 0.10 and effective >= 2.0` 才允许 `_update_profile`。
按 R1 的表，`0.88` 的可达率是 **0.08%**。也就是说：

> **每个 profile 建立之后，终身停留在 1 条观测上，永远不会变好。**

系统里最强的杠杆被一个常量关掉了，剩下四张 ticket 的状态机再精巧也无从发力。

### R3 — 输入侧三项「预处理」：一项 no-op，两项负收益

**(a) `_apply_pcm_gain` 只放大、不衰减 —— 实质 no-op。**
`speaker_attribution.py:147` 的 `gain = min(max_gain, peak_gain, max(1.0, requested))`，
`max(1.0, ...)` 让所有需要衰减的片段原样返回。实测：

```
target = -20.0 dBFS
ANG_HI  -16.50 -> -16.04   (需要衰减，实际 +0.46)
SAD_LO  -40.64 -> -28.64   (需要 +20.6，被 max_gain_db=12 截断)
响度极差  36.8 dB -> 24.8 dB     衰减过的片段: 0/240
```

这批数据的**响度和情绪是完全共线的**（ANG_HI 比 SAD_LO 响 24 dB），本来正是要消除的混淆，
结果处理完还剩 24.8 dB 且共线关系原封不动。顺带：21/240 条本身已削顶，增益也救不回来。

*不过*——实测两侧都做的正确响度归一化，EER 只从 27.48% 变到 27.43%。**响度根本不是瓶颈**
（CAM++ 的 fbank 前端自带均值归一）。所以这个 bug 该修，但修完不要期待收益。

**(b) pooling 窗口比音频还长 —— 对 2/3 的数据是字面意义的 no-op。**
`window_seconds=2.5` 而 clip 中位时长 2.34s。实测 `observe_embedding` 的窗口数分布：
`{1: 159, 2: 77, 3: 3, 4: 1}` —— **66% 的 clip 只有一个窗口**。
`POOLED_RAW_ALGORITHM` 里写的 `"trim-gain-2.5s-1.25s-normalized-mean"` 对多数样本名不副实。

**(c) 而且 pooling 一旦真的生效，是负收益。**

| 输入处理 | 全对 EER | 跨情绪 EER |
|---|---:|---:|
| 整句、零预处理 | **20.83%** | 22.21% |
| + 边缘静音裁剪 | 21.82% | — |
| + 内部静音裁剪并拼接 | 27.48% | 29.35% |
| + 两侧响度归一化 | 27.43% | 29.43% |
| + pooling 1.5s / 0.75s | 32.51% | 35.00% |
| + pooling 1.0s / 0.5s | **38.64%** | 41.20% |

原因由下面这条曲线解释 —— **EER 几乎完全由「喂进模型的语音秒数」决定**：

| 有效语音 | EER |
|---:|---:|
| ~3.2s | 28.35% |
| ~6.5s | 18.02% |
| ~10.6s | 9.93% |
| ~13.1s | 7.00% |
| ~21.2s | **2.34%** |

切窗 = 缩短每个 embedding 看到的语音 = 沿这条曲线往上走。平均多个更差的向量，
补不回被切掉的信息。**这一条同时证伪了我上一版方案的 L1.1 和 L1.3。**

唯一被验证有效的打分改动是 **centering**（减全局均值）：20.83% → 17.48%，稳定但幅度有限。
**AS-Norm 实测没有帮助**（centering 后 28.17% → 29.17%）—— cohort 只有 18 个 actor、
且录音条件单一，z-score 的统计量估不准。上一版方案把它列为「收益最大的一步」是错的，
至少在这个数据规模上不成立。

### R4 — 这个 benchmark 数学上就通不过，而且没人算过天花板

我实测了**离线上界**：把每个 session 的 24 条全部拿到手、告诉它答案就是 3 个人、
无限算力跑平均连接层次聚类：

```
ORACLE-k 离线 AHC，raw cosine : B³ F1 = 0.692   accuracy = 0.690
ORACLE-k 离线 AHC，centered   : B³ F1 = 0.657   accuracy = 0.702
```

**任何在线算法都不可能超过 ~0.69。** 而已交付的 robust 版本是 0.598 —— 已经是天花板的 87%。

`evaluate_release_gate()`（`crema_mini.py:378-386`）同时要求
`false_split ≤ baseline×0.5` **且** `false_merge ≤ baseline+0.01` **且**
`unknown ≤ baseline+0.05` **且** `B³ ≥ baseline`。在一个天花板 0.69、
单句 EER 20% 的数据上，这组约束没有可行解。

**五张 ticket 的工作量，是花在追一个可以事先证明不可达的目标上的。**
天花板计算是 30 行代码，本该是 Ticket 01 的第一件事。

### R5 — benchmark 复现的是和用户报告相反的故障

实测冻结 legacy baseline（threshold=0.4，即生产默认值）在这批数据上：

| | false_split | false_merge | UNKNOWN | B³ F1 |
|---|---:|---:|---:|---:|
| legacy @0.4（calibration） | 0.033 | **0.537** | 0.000 | 0.615 |
| legacy @0.4（evaluation） | 0.004 | **0.662** | 0.000 | 0.502 |

**legacy 在这里的故障模式是「把 3 个人全并成 1 个」，不是「把 1 个人拆成多个」。**

用户报告的生产症状是同一个人换语调后被标成新说话人（over-split）。
这个 benchmark 上 legacy 的 false_split 是 **0.004**。也就是说，
**它从一开始就没有复现要修的那个 bug**，后续所有针对它的优化都在往反方向使劲 ——
这解释了为什么 robust 版本的 false_split（0.306）反而比 legacy（0.004）高了 75 倍还被当成进步。

附带的口径问题：负样本被强制约束为**同性别 + 同情绪 + 同强度 + 同一句台词（IEO）**
（`crema_mini.py:223-229`），是最对抗的构造；正样本则跨情绪。这样得到的 pair EER
既不能横向对比，由它导出的阈值也系统性偏离 session 任务的真实工作点。handoff 里
把 `match_threshold` 直接取自这个 EER threshold，是错上加错。

### R6 — 真正卡住分数的是 session 结构，不是算法

我做了一个干净的消融：**同样的 24 条 clip、同样的 3 个说话人、同样的算法，
只改说话人轮换的粒度**（不复用任何 clip）：

| 每人连续发言条数 | false_split | false_merge | UNKNOWN | B³ F1 | churn |
|---|---:|---:|---:|---:|---:|
| 1（最大交替） | 0.359 | 0.287 | 0.042 | 0.582 | 0.219 |
| **2（= 当前 benchmark）** | 0.328 | 0.316 | 0.043 | **0.595** | 0.215 |
| 4 | 0.253 | 0.244 | 0.044 | 0.693 | 0.167 |
| **8（≈ 真实直播）** | **0.101** | 0.173 | 0.026 | **0.822** | 0.129 |

当前 benchmark 的说话人切换率是 **48%**（220/460 相邻对），平均连续发言 **2.00 条**，
每人每 session 只有 8 条、总共 56 秒音频。真实直播是一个人连说十几句、两三个固定说话人、
持续几十分钟。**B³ 从 0.595 到 0.822 完全来自结构差异，算法一行没改。**

CREMA-D mini 是一个**选错了的代理任务**：英语情绪表演、2.4 秒单句、极高切换率，
与日语直播的分布差得很远。

## 2. 我实测的修正版算法：证明「没有信号可挖」

为了确认上面的诊断，我实现了一版修正算法（centering + **无门槛 profile 累积** +
按实际尺度标定的阈值 + 连续性 + reconciliation），只在 calibration split 上做小网格选参，
evaluation 只报一次：

| | false_split | false_merge | UNKNOWN | B³ F1 |
|---|---:|---:|---:|---:|
| legacy baseline（eval） | 0.004 | 0.662 | 0.000 | 0.502 |
| 已交付 robust（eval，handoff 数字） | 0.306 | 0.274 | **0.742** | 0.598 |
| **本次修正版（eval）** | 0.397 | 0.319 | **0.046** | 0.559 |
| 离线 ORACLE-k 天花板 | — | — | 0 | 0.657–0.692 |

修正版把 UNKNOWN 从 **74.2% 打到 4.6%**，但 B³ 基本没动。这正是关键证据：

> 已交付版本不是「算法差」，是「拒绝作答」。修正之后它愿意作答了，
> 准确率却没提升 —— 因为在 2.4 秒单句这个工作点上，**信息量本身就到顶了**。

同一套算法换到 run-length=8 的结构上是 B³ **0.822**。所以：**算法没问题，工作点有问题。**

## 3. 改进方案

### P0 — 止血（半天）

1. `.scratch/.../05-reconcile-remap-release.md` 状态改为 **release blocked**，
   理由写「gate 目标超出 benchmark 理论上界（实测 0.69）」，不是「参数没调好」。
2. `benchmark-results/crema-mini/*.json` 全部作废并加 `INVALID.md` 说明原因，
   防止后续会话把 0.598 当成有效基线继续对比。
3. 在 `crema_mini.py` 顶部加一行注释指向本文。

### P1 — 修四个确定性缺陷（1 天）

| # | 位置 | 修法 |
|---|---|---|
| 1 | `AssignmentConfig`（`speaker_attribution.py:236-258`） | **全部阈值重新标定**。禁止手写常量；改为从 calibration session 网格选出并写进 report 的 fingerprint。工作尺度参考：centering 后同人 p50 ≈ 0.30、异人 p95 ≈ 0.25 |
| 2 | `assign()` 的 profile 更新门（`:432-438`） | **拆掉高门槛累积**。凡是 `confirmed_existing` 就并入 profile 的求和向量；只用「质量 flag + 最短有效时长」做准入，不用相似度做准入。这是 R2 的 13 倍杠杆 |
| 3 | `_apply_pcm_gain`（`:147`） | 去掉 `max(1.0, requested)`，做两侧归一化；或者干脆删掉这个函数（实测收益 ≈ 0.05% EER） |
| 4 | `observe_embedding` 的 pooling（`:193-211`） | **删掉**。实测 20.83% → 32.51% 的负收益。整句直接 embed，不裁剪、不切窗 |

净效果是**代码变少**：Ticket 03 的输入侧管线（trim / gain / pooling）应当整体移除，
只保留 `EmbeddingObservation` 这个数据结构和 centering。

### P2 — 重建 benchmark（2 天）**← 最重要的一步**

现有 benchmark 必须重做，四条硬性要求：

**(a) 先算天花板，再定 gate。**
新增 `benchmarks/ceiling.py`：对每个 session 跑 oracle-k 离线 AHC，输出 B³ 上界。
**release gate 的目标值必须表述为「天花板的百分比」**（例如 ≥ 0.85×ceiling），
绝对值 gate 一律不接受。这一条如果早做，能省下四张 ticket。

**(b) benchmark 必须先复现要修的 bug。**
加一个**准入自检**：跑 legacy baseline，如果它的 `false_split` 不显著高于 `false_merge`，
就 **fail fast 并拒绝出报告** —— 说明这个数据集复现的不是生产症状，用它调优是有害的。
当前数据集会在这一步直接被拒（0.004 vs 0.662），这正是它应有的结局。

**(c) 修 session 结构，贴近直播。**
- 每人连续发言 4–8 条（当前是 2），切换率降到 10–20%
- 每 session 至少 5 分钟音频、每人至少 20 条（当前 56 秒 / 8 条）
- 说话人 2–3 人（保持）

**(d) 修 utterance 时长分布 —— 这是最关键的一条。**
CREMA-D 的 2.4 秒单句在 EER 曲线上是最差的一段。用**同一 actor 的 2–3 条不同情绪 clip 拼接**
构造 3–7 秒的合成 utterance：既得到了真实直播的时长分布，
又让「一句话内部包含语调突变」成为默认情形 —— 正好是要测的东西。
这不是作弊，是把代理任务的工作点对齐到生产工作点。

**(e) 负样本口径分层。**
主指标用代表性分布（不强制同性别/同情绪）；把当前的
「同性别+同情绪+同强度+同台词」保留为一个显式标注的 **hard subset**，只做诊断，不喂阈值标定。

**(f) 补一个真实域 smoke set（不可替代）。**
从实际日语直播抠 10 分钟，人工标 2–3 个说话人。CREMA-D 是英语情绪表演，
永远不能作为业务域的最终保证。这一条不做，前面全部只是自娱自乐。

### P3 — 算法：把赌注全部押在证据累积上（2 天）

按实测，只有三件事有效，其余全部删掉：

**(1) 跨句证据累积（13× 杠杆）** —— profile 保存**所有**被判为该说话人的观测的求和向量，
无上限累积；匹配时用累积中心。P1-#2 已经解决准入问题，这里补上：
- 累积中心 + 最多 4 个子中心（保留多语调建模），子中心准入门槛按实际尺度重标
- 只有明确低置信的观测（quality flag / 有效语音 < 1s）才不并入

**(2) 全局 centering** —— 唯一验证有效的打分改动（20.83% → 17.48%）。
用滑动均值，样本数 < 8 时不启用。**不要做 AS-Norm**（实测负收益，cohort 太小）。

**(3) 新增：turn 级证据合并（这是生产侧最大的一步，benchmark 上看不到）**
既然 EER 由累计语音秒数决定，就不要按 ASR 的单句去做归属。在
`SubtitlePipeline._attribute_speaker` 之前加一层聚合：**把 gap < 0.8s 的连续句合并成
一个 ≥ 4s 的证据块再送去 embed**，一次决策覆盖整个 turn 的所有 cue。
直播里一个 turn 通常被 ASR 切成 3–5 句，合并后有效时长从 2.4s 拉到 6–10s ——
按实测曲线，这一步是 **28% → 10% EER**，比所有打分技巧加起来都大。
延迟代价：一个 turn 的尾句晚 1–2 句上色，而归属本来就是 late-fix 的
（`subtitle_pipeline.py:888`），架构上零成本。

**保留**：迟滞双阈值、连续性先验、candidate 确认延迟、reconciliation 合并回写
（R6 的 churn 从 0.219 降到 0.129 有它们的贡献）。**阈值全部按 P1-#1 重标。**

**删除**：`observe_embedding` 的 trim/gain/pooling、AS-Norm（如已实现）、
`merge_immediate_threshold=0.97` 这类死路径。

### P4 — 重新定义 release gate（半天）

```
gate = {
  ceiling_ratio  : candidate.b3 >= 0.85 * oracle_ceiling_b3      # 相对，不是绝对
  split_reduction: candidate.split <= baseline.split * 0.5       # 保留，但前提是 (b) 自检通过
  merge_guard    : candidate.merge <= baseline.merge + 0.02
  unknown        : candidate.unknown <= 0.10                     # 绝对上限，防「拒绝作答」刷分
  latency        : 真实 enqueue→first-decision p95 < 500ms
}
```

外加一条硬约束：**`unknown` 必须有绝对上限**。已交付版本用 74% 的 UNKNOWN
换来了漂亮的 split/merge 数字，现有 gate（`unknown ≤ baseline + 0.05`）在 baseline=0 时
本该拦住它，但整个 gate 从没真正跑过。**gate evaluator 必须先在已知失败样本上验证它会 fail。**

同时修 handoff 第 4 步提到的问题：当前 latency 测的是 gallery 决策的 CPU 时间
（p95 输出 0.0ms），不是 spec 定义的 enqueue → first decision。这个 seam 要么真做，
要么把这条 gate 明确标为「未测量」，不要留一个 0.0ms 的假绿灯。

## 4. 为什么论文说 0.7%，我们测出 20.8%？（完整拆解）

模型没有坏，也没有装错。**0.7% 和 20.8% 测的根本不是同一件事。** 逐项实测拆解：

| 条件 | 实测 EER |
|---|---:|
| 我们的工作点：2.4s 单句 + 全部负样本 | **20.83%** |
| 负样本只留跨性别（≈ VoxCeleb 的负样本难度） | 13.33% |
| 负样本只留同性别 | 27.95% |
| 负样本同性别 + 同情绪 + 同台词（= 当前 benchmark 的构造） | 33.26% |
| 正样本只留同情绪（无语调变化） | 12.85% |
| 正样本只留跨情绪（有语调变化） | 22.21% |
| 时长 2.4s → 4.8s | 19.00% → 12.00% |
| 时长 → 7.2s → 9.6s → 14.4s | 7.98% → 4.33% → 2.26% |
| **~9.6s 片段 + 跨性别负样本（≈ VoxCeleb 协议）** | **0.92%** |

最后一行就是答案：**把条件还原成 VoxCeleb 的测试协议，这个模型在我们自己的数据上就是 0.92%**，
和公开的 0.7% 完全对得上。20.8% 里没有一分钱是模型缺陷，全部来自协议差异：

1. **时长（最大项）**。VoxCeleb-O 的测试片段平均 ~8 秒，我们是 2.4 秒。单这一项就是 19% → 4.3%。
2. **负样本难度**。VoxCeleb 的负样本对是随机配的，约一半跨性别；我们要求区分的是
   同一场直播里的 2–3 个人，很可能同性别。13.33% vs 27.95%，差一倍。
3. **没有信道线索**。VoxCeleb 里不同说话人来自不同视频、不同录音设备，embedding 编码了
   「说话人 + 信道」，负样本两者都不同 → 容易拒绝。CREMA-D 的 20 个演员在同一间棚、
   同一支麦、念同一句台词，**负样本只差在嗓音本身**。这一项在 CREMA-D 内部无法消融，
   但它是「同一个直播间的两个人」的真实写照。
4. **语调变化**。同情绪 12.85% vs 跨情绪 22.21% —— 用户报告的症状本身，贡献约一倍。

所以正确的结论是：**「CAM++ 有 0.7% 的 EER」这句话，在我们的场景里从来就不成立**，
不是模型退化了，是把一个长片段、跨信道、随机负样本的数字，套到了一个短片段、
同信道、同性别负样本的任务上。上一版方案里我引用 0.6–0.7% 来说明「这个数字是灾难性的」，
判断方向对（当时确实有 bug），但那个对比本身是不公平的，这里更正。

## 5. 换模型：实测六个候选

既然主要矛盾是时长和任务难度，换模型的收益需要实测而不是看排行榜。
六个候选全部在**本项目的这批数据**上跑（CPU，4 线程）：

| 模型 | 体积 | dim | RTF | 2.4s | 同性别负样本 | 跨情绪 | 4.8s | 7.2s |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| CAM++ `zh-cn`（**当前**） | 28MB | 192 | 0.0043 | 20.83% | 27.95% | 22.21% | 11.33% | 7.02% |
| **CAM++ `zh_en_advanced`** | **27MB** | 192 | **0.0043** | **15.68%** | **19.32%** | **17.20%** | **5.33%** | **3.32%** |
| ERes2NetV2 `zh-cn` | 68MB | 192 | 0.0137 | 19.85% | 26.06% | 21.20% | 9.33% | 6.67% |
| TitaNet-L `en` | 97MB | 192 | 0.0076 | 16.22% | 20.07% | 17.22% | 5.67% | 2.66% |
| wespeaker CAM++ `en` | 28MB | 512 | — | *无效* | | | | |
| wespeaker ResNet293-LM `en` | 109MB | 256 | — | *无效* | | | | |

**结论一：应该换，而且是免费的。**
`3dspeaker_speech_campplus_sv_zh_en_16k-common_advanced` 是**同架构、同体积（27 vs 28MB）、
同速度（RTF 相同）、同接口**（3d-speaker 框架、192 维、相同 metadata）的直接替换件，
在每一个工作点上都优于当前模型：2.4s 上 20.83% → 15.68%（相对 -25%），
7.2s 上 7.02% → 3.32%（相对 **-53%**）。改动只是
`scripts/download-diar-models.py` 里的 URL 和 SHA-256 两行。

**结论二：更大的模型不划算。**
ERes2NetV2 体积 2.4 倍、耗时 3.2 倍，收益只有 20.83% → 19.85%（几乎在噪声内）。
TitaNet-L 和 zh_en advanced 打平，但体积 3.6 倍、耗时 1.8 倍，且是纯英文模型。
**这条曲线上「换更大的模型」的边际收益远小于「换对训练域」和「加长片段」。**

**结论三：两个 wespeaker 模型的数字无效，不能当作质量结论。**
它们在 sherpa-onnx 1.13.6 下的 embedding 明显塌缩 —— ResNet293 的全体两两余弦
mean=0.836 / sd=0.068，男声(1001)与女声(1002)的质心余弦高达 **0.906**。
按 int16 量纲重喂（`normalize_samples=0`）也没有改善（46.06% → 42.42%）。
这是特征链路不匹配，不是模型能力。想用 wespeaker 系需要先单独排查，本次排除。

### 端到端验证（session 级，用第 2 节的修正算法）

| 模型 | 每人连续发言 | false_split | false_merge | UNKNOWN | B³ F1 | churn |
|---|---|---:|---:|---:|---:|---:|
| CAM++ zh-cn（当前） | 2（当前 benchmark） | 0.328 | 0.316 | 0.043 | 0.595 | 0.215 |
| CAM++ zh-cn（当前） | 8（≈真实直播） | 0.101 | 0.173 | 0.026 | 0.822 | 0.129 |
| CAM++ zh+en advanced | 2（当前 benchmark） | 0.282 | 0.237 | 0.054 | 0.671 | 0.143 |
| **CAM++ zh+en advanced** | **8（≈真实直播）** | **0.059** | **0.136** | 0.036 | **0.873** | **0.090** |

换模型让 false_split 再降 42%（0.101 → 0.059），churn 降 30%，B³ 到 0.873。

### 三个杠杆的相对大小（这是最该记住的一张表）

| 动作 | EER（单句 → 目标工作点） | 成本 |
|---|---|---|
| P3-(3) turn 级证据合并（2.4s → 7.2s） | 20.83% → 7.02% | 一层聚合逻辑，零架构成本 |
| 换 `zh_en_advanced` checkpoint | 20.83% → 15.68% | **两行 URL/SHA** |
| **两者叠加** | **20.83% → 3.32%** | — |
| 换更大模型（ERes2NetV2/TitaNet） | 20.83% → 16~20% | 体积 2.4–3.6×，耗时 1.8–3.2× |

**先做前两项，它们叠加是 6.3 倍的误差下降，成本几乎为零；更大的模型不必上。**

### 必须说清楚的三条限制

1. **本次全部在英语 CREMA-D 上测，产品域是日语直播。** 当前模型是纯中文训练，
   `zh_en_advanced` 是中英训练，TitaNet-L 是纯英文 —— **英语测试集天然偏袒后两者**。
   日语两个模型都没训过。`zh_en_advanced` 覆盖的语言是当前模型的超集、
   体积速度不变、在这里全面更优，所以换过去是**低风险**的；
   但「换了在日语上一定更好」这句话本次数据支持不了，必须在 P2-(f) 的真实直播 smoke set 上复验。
2. 说话人 embedding 主要编码音色而非语言内容，跨语言迁移通常还行，但这是通则不是保证。
3. 六个模型只测了余弦 EER 和 session B³，没测抗噪/抗 BGM。直播有 BGM，
   这一维要在真实 smoke set 上单独看。

### 外部交叉验证：pyannote 在日语上是最差的选项

查到一篇有 JVS 日语实测的论文（arXiv:2503.10446，Whisper Speaker Identification）：

|---|---:|
| WSI（该论文方法） | 8.48% |

| X-vector | 21.23% |

两个结论：
1. **20% 量级的 EER 在这类任务上是常态，不是我们装错了。** 我们 CAM++ 在英语 CREMA-D

2. **pyannote 的 embedding（26.39%）比 ECAPA 还差。** 你最初提到在用 pyannote ——
   如果那条链路真的存在，换回或换去 pyannote 都是**降级**。
   顺带：pyannote 3.1 的 embedding 就是 `wespeaker_en_voxceleb_resnet34_LM`，

**n=1 → n=2 就是 4 倍误差下降**，这一步最可信也最容易拿到。
（诚实标注：只有 4 个说话人，n≥3 的亚 1% 数字被显著高估，不要当承诺；
n=1→n=2 这一步是可信的。）这与 §2/§4 在英语上的结论方向完全一致 ——
**turn 级证据合并 + profile 无门槛累积，仍然是杠杆最大的一步，换模型排第二。**

4. 最终仍然需要 P2-(f) 的**真实日语直播人工标注 smoke set**。JVNV 只是把结论
   从「英语情感表演」推进到「日语情感朗读」，离「日语直播」还差一步。

## 5.6 性能实测：ERes2Net large 被否掉，选 `zh_en_advanced`

§5.5 里我按 RTF 0.042（4 线程）说 ERes2Net large「实时只占单核 4.2%」。
按生产实际条件（`diar_sherpa.py` 默认 `num_threads=1`）重测后，**这个说法是错的**，
纠正如下。

**先回答 GPU**：都不需要，也用不上。本机 onnxruntime 只有
`['AzureExecutionProvider', 'CPUExecutionProvider']`，没有 CUDA provider；
sherpa-onnx 的 `SpeakerEmbeddingExtractor` 在这里就是纯 CPU 路径。
换 GPU 需要换整个构建，不在范围内。

| 模型 | 磁盘 | 常驻内存 | 加载 | **3s/1线程** | **6s/1线程** | 3s/4线程 | RTF@1线程 |
|---|---:|---:|---:|---:|---:|---:|---:|
| CAM++ `zh-cn`（当前） | 27M | 73M | 0.36s | **19.9ms** | 37.8ms | 12.1ms | 0.0066 |
| **CAM++ `zh_en_advanced`** | **27M** | **51M** | 0.31s | **19.5ms** | **36.4ms** | 11.3ms | **0.0065** |
| ERes2NetV2 `zh-cn` | 68M | 134M | 0.24s | 117.8ms | 247.0ms | 38.5ms | 0.0393 |
| ERes2Net large `zh-cn` | 210M | 289M | 0.76s | **373.2ms** | **784.8ms** | 122.0ms | 0.1244 |

### 为什么否掉 ERes2Net large

1. **它和本方案最重要的一步互斥。** P3-(3) 的 turn 级证据合并要把片段拉到 6–10 秒，
   而 ERes2Net large 处理 **6 秒要 785ms（单线程）**，spec 的
   「enqueue → first decision p95 < 500ms」这一条**它自己就过不去**，
   还没算排队。越是把方案做对，它越过不去。
2. **19 倍 CPU 换 18% 相对收益。** 相对免费的 `zh_en_advanced`：
   3s 上 7.34% vs 8.90%，但单次耗时 373ms vs 19.5ms。
3. **常驻内存 289M vs 51M**，对一个要和浏览器、播放器、ASR、翻译共存的桌面伴侣应用不划算。

### 为什么 ERes2NetV2 也否掉

它比免费的 `zh_en_advanced` 只好 **0.26 个百分点**（日语 3s：8.64% vs 8.90%），
却要 **6 倍 CPU（117.8ms vs 19.5ms）和 2.6 倍内存**。不值。

### 决定性的一条：免费模型 + 长片段，打赢昂贵模型 + 短片段

| 组合 | 日语 EER | 单次耗时（1 线程） |
|---|---:|---:|
| 当前模型 @ 3s | 10.67% | 19.9ms |
| ERes2Net large @ 3s | 7.34% | 373ms |
| **`zh_en_advanced` @ 6.5s（turn 合并后）** | **6.53%** | **36.4ms** |

**`zh_en_advanced` + turn 合并，比 ERes2Net large + 不合并更准，而且快 10 倍。**
这正是 §2/§4 的主线结论在成本维度上的再次印证：**工作点比模型重要。**

**结论：换 `3dspeaker_speech_campplus_sv_zh_en_16k-common_advanced`。**
同磁盘、更省内存（51M vs 73M）、同延迟、日语上全面更优（3s -17%，同性别 -19%，full -23%）。
成本是 `scripts/download-diar-models.py` 里的 URL + SHA 两行。

## 5.7 那么，几件事都要做吗？——不都做

按「实测收益 ÷ 成本」排序，明确分成三档：

### 必做（三件，其中两件是修 bug 不是增强）

| # | 事项 | 实测依据 | 成本 |
|---|---|---|---|
| 1 | **turn 级证据合并**（gap<0.8s 的连续句合并成 ≥4s 证据块再 embed） | 日语 10.67%→6.53%；累积 n=1→n=2 是 7.54%→1.89% | 一层聚合逻辑，归属本来就是 late-fix，零架构成本 |
| 2 | **修阈值量纲 + profile 无门槛累积** | 0.82/0.88/0.90 在日语上可达率同样接近 0；日语实测工作点是 raw≈0.49 / centered≈0.15 | 改常量 + 拆掉一个 if |
| 3 | **换 `zh_en_advanced` checkpoint** | 日语 3s -17%，同性别 -19%，成本零 | 两行 URL/SHA |

第 2 件必须理解为**修 bug**：当前配置让新说话人几乎无法确认（74% UNKNOWN）、
profile 终身停在 1 条观测。不修它，第 1 件的收益也拿不到 —— 因为累积机制是关着的。

### 顺手做（都是删代码）

| 4 | **删掉 `observe_embedding` 的 pooling / trim / gain** | pooling 实测 20.83%→32.51% 负收益；gain 是 no-op（0/240 被衰减）；trim 中性偏负 |
| 5 | **加 centering** | 英语 20.83%→17.48%，日语 11.00%→7.54%，唯一验证有效的打分改动 |

### 明确不做

| 事项 | 否掉的实测理由 |
|---|---|
| ERes2Net large / ERes2NetV2 | 19x / 6x CPU 换 18% / 3% 收益，且 large 破坏 500ms 延迟门 |
| AS-Norm | 实测 28.17%→29.17%，负收益（cohort 太小） |
| 多子窗 pooling | 实测负收益，见上 |
| 换 pyannote embedding | JVS 上 26.39%，是查到的所有模型里最差 |
| GPU 加速 | 不需要；当前构建也没有 CUDA provider |

### 但有一件不能省：benchmark 重建

第 1–5 件做完，**没有一个可信的 benchmark 就无法判断它们是否生效**，
而现在这个 benchmark 已经被证明连要修的 bug 都复现不了（§R5）。
最小可接受版本是 P2 里的两条自检：**先算天花板**、**先验证 legacy 在数据上确实过度拆分**。
这两条加起来半天，是唯一能防止再来一轮「五张 ticket 白做」的东西。

## 6. 需要你拍板的范围问题

不换模型的上限已经量化清楚了：turn 合并把工作点推到 6–10 秒后，
当前模型是 EER ~7%，换 `zh_en_advanced` 是 ~3.3%。

我的建议是**换 checkpoint 但不换架构** —— 它不违反「不引入 pyannote 全量管线 /
不微调」的范围约束，成本是两行常量，收益在本数据上是全面的。这一条需要你确认，
因为它改变了 `vendor/models/` 的产物和 NOTICE 归属。

真正要你拍板的只有一个：**P2-(f) 的真实直播 smoke set 什么时候做。**
上面所有结论都建立在一个英语情绪表演数据集上，而它已经被证明连要修的 bug 都复现不了。
在拿到 10 分钟真实日语直播的人工标注之前，任何模型选型结论都只是候选，不是定论。

## 5. 执行顺序与验收

| 阶段 | 内容 | 工作量 | 验收 |
|---|---|---|---|
| P0 | 止血、作废无效结果 | 0.5 天 | ticket 状态诚实反映 blocked |
| P2a | 天花板计算 + benchmark 症状自检 | 0.5 天 | 现有数据集在自检处被拒绝 |
| P1 | 四个确定性缺陷 | 1 天 | pooling/trim/gain 代码删除；profile 累积可达率 > 80% |
| P2b–f | 重建数据集（结构 + 时长 + 分层 + 真实 smoke） | 1.5 天 | legacy 在新集上 false_split > false_merge |
| P3 | 证据累积 + centering + turn 合并 | 2 天 | 在新集上 B³ ≥ 0.85×ceiling，UNKNOWN < 10% |
| P4 | 重定 gate 并在已知失败样本上自验 | 0.5 天 | gate 对已交付 74%-UNKNOWN 版本判 fail |

**先做 P2a。** 半天的天花板计算能决定后面 5 天值不值得投 —— 这正是上一轮缺失的那一步。
